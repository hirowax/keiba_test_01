# 採点に使うページの取り直しの計画（2026-11-13 作成・未承認）

v5.2 の採点（`run_pickup_all.py`）で、出馬表・データ分析のページに取得異常があったレースのページを、入力の確定の期限より前に取り直すかどうかの計画。
v5.2 の計画書（`docs/data_top_reader_fix_plan_202611.md` の 2026-11-09 の項）で「取り直しを足すときは、別の変更として先に決める」とした事項を決める。
**この文書はまだ承認されていない。実装はしない。** 2026-11-13 の外部レビューで、本番の v5.2 の採点の取得異常を数週観察してから実装の要否を決める順番になった（7章）。

## 0. 今わかっていること（2026-11-13 にコードとファイルで確かめた）
- 本番の v5.2 の採点はまだ1回も動いていない。最初は 2026-11-13 17:00（対象日 11/14）。保存済みの `pickup_scores.json` は 11/8 までで、どれも v5.1（`quality.data_top_issues` が無い）。本番での取得異常の件数・種類は、まだ分からない。
- 手元の例は、本番とは別のフォルダでの確かめの採点だけ（`docs/data_top_reader_fix_plan_202611.md`）:
  - 11/8 京都4R: 前日 20:43 のデータ分析のページに、出走馬分析の表が無かった（前日でも出ないレースがある）。
  - 11/8 東京11R: 出走馬分析の欄の前に「レース分析」の欄があり、知らない見出しとして取得異常にしていた（読み取りの不具合。2026-11-09 に直した）。
  - 11/9 16:54 に東京11R を1回取り直すと、普通のレースと同じ欄があった。
- 3項目の取得異常は `quality.data_top_issues`、ページの保存先と失敗は `quality.pages` に記録され、どちらかがあれば `data_quality.race_quality_issues()` で問題ありになる（🔥・買い目・評価から外れる）。
- `rerun_failed_pickup.py` の再実行の対象（`needs_rerun()`）は、採点エラー・候補全員0点かつ人気が空・前走データの取得失敗だけ。3項目の取得異常・ページの保存の失敗だけのレースは対象にならない。

- `rerun_failed_pickup.py` は、取り直したレースの採点で `pickup_scores.json` のそのレースを置き換える（前の採点は、そのファイルには残らない。前走データの記録 `prev_inputs/{実行ID}.json` とページは残る）。
- 軸の記録（`axis_record.py record`）は 17:00 の採点の直後に書き、書き換えない。取り直した採点は、今の規則では軸の記録に入らない。

## 1. 対象にする異常
取り直しで直る見込みがある、一時的な異常だけを対象にする。読み取りの規則の問題で、取り直しても同じになるものは対象にしない（その場合はコードを直す別の変更）。

| 異常（`data_top_issues`・`pages` の文字） | 取り直すか | 理由 |
|---|---|---|
| データ分析: 公開されていない | する | 取得の時刻で変わる（前日の夕方は未公開のことがある） |
| データ分析: 欄が無く、公開されていない案内も無い／ページの形が違う（見出しが無い） | する | ログインの案内・エラーのページの可能性。ただし2回続けば止める（下の「回数」） |
| 出走馬分析: 数える表が無い／欄が無い、ピックアップ: 欄が無い | する | 京都4R の例（前日でも出ないことがある） |
| 上位3頭: 出馬表に欄が無い／欄はあるが表が無い | する | 同上 |
| ページの保存に失敗（`pages` の error） | しない（2026-11-13 外部レビュー） | まず保存の環境（ディスクなど）を直す対象。取得済みのページを保存し直せるなら、netkeiba へ取りに行き直さない |
| 知らない見出し・同じ見出しの表が2つ・読めない形・馬番が2回ある・出馬表と照らせない | しない | 読み取りの規則か、ページの仕様の問題。取り直しても直らない見込み。件数と一覧を報告して、コードを直すか決める |
| 採点エラー・前走データの取得失敗など | 今までどおり `needs_rerun()` | 変えない |

- 1つのレースに「しない」の異常が1つでもあれば、そのレースは取り直さない。

## 2. 回数・時刻・期限・アクセス数
- 期限: 対象日の 00:00（日本時間）。前走データ・脚質・軸の記録と同じ、入力の確定の期限。どのレースも発走は期限より後なので、期限前の取得は発走前の情報だけになる。
- 時刻: 17:00 の本番の後、**22:30 に1回だけ**取り直す（案）。cron に1行足す（`run_cron.sh` と同じく、翌日が開催日のときだけ）。
  - 22:30 にする理由: 京都4R の例では前日 20:43 に表が無く、翌日 16:54 にはあった。何時に出るかは確かめていないので、期限の前のできるだけ遅い時刻にする。採点と保存（1レースおよそ1分）が 00:00 までに終わる余裕を残す。
- 回数: 1つのレースにつき、取り直しは1回まで（17:00 と 22:30 の2回で終わり）。
- 取り直すレースの数: 1回で最大12レース（暫定案）。上限を超える日は、レースIDの順に12レースまでにして、残りを件数で報告する。
- アクセス数の上限（2026-11-13 外部レビュー: 12レースはアクセス数の上限ではない）: 1回の取り直しで netkeiba へのページの移動を最大60回（暫定案）とし、出馬表・データ分析・前走データの馬ページ（`reusable_entries` で再利用できない馬）・中間ページ（`human_browse`）・再試行をすべて数える。上限に達したら、その時点で止めて、取り直せなかったレースを件数と一覧で報告する。上限の値は、観察の期間に、1レースあたりの実際の移動の回数を見てから決め直す（決め直すのは実装の前で、成績は見ない）。
- cron への追加は、まだ行わない（2026-11-13 外部レビュー）。
- 止める条件: 今の取得と同じ（IPブロックの検知・連続の失敗で止める。`scraper` の安全弁）。

## 3. 元のページと採点の記録を残す方法
- ページ: 今までどおり、取り直しの実行IDのフォルダに保存し、前の実行のページは置き換えない。
- 採点: 取り直す前に、そのレースの前の採点（`pickup_scores.json` のそのレースの中身）を `output/{日}/pickup_reruns/{実行ID}.json` に書き出してから置き換える（案）。書き出せなければ取り直さない。
- 取り直した採点の quality には、取り直しであること・前の実行ID・取り直した理由（どの異常だったか）を足す。
- 期限（対象日 00:00）をまたいだ取り直しは、元の採点を置き換えない（2026-11-13 外部レビュー）。期限の前に始めても、保存の前に期限を過ぎていれば、取り直しの結果は `pickup_reruns/` に「期限後」として残すだけにする。

## 4. 評価に使う採点の選び方
- サイトの表示・品質の判定: 期限前に終わった最新の採点（取り直した後なら、取り直しの採点）。
- 軸の再検証（`docs/axis_recheck_plan_202611.md`）: **取り直した採点を入れない**（案）。軸の記録は 17:00 の採点の直後に書き、書き換えない規則のままにする。
  - 入れる場合は、軸の記録の規則（書き換えない・復元は記録の無いレースだけ）を変えることになり、計画 4.3 の「影響あり」になる。その場合は別に決める。
  - **実装の前に要ること（2026-11-13 外部レビュー）**: 今の `axis_record.py restore` は、期限前に GitHub の main にあった最後の commit の入力で計算し直す。取り直しの採点が期限前に push されていると、記録が欠けたレースの復元に、取り直した後の採点が入り得る。復元でも最初の採点（17:00 の本番の採点）を使う仕組み（例: 取り直したレースは `pickup_reruns/` に書き出した前の採点を使う）を、取り直しの実装と一緒に入れる。
- 将来の🔥の基準・研究: 「期限前に終わった最新の採点」を使い、取り直したレースの件数と一覧を必ず出す（17:00 の時点で異常だったレースが、取り直しで評価に戻ったことが分かるように）。17:00 の採点だけで集計した場合と、件数を並べて報告する。
- 期限後に終わった取り直しは、評価に使わない（`rerun_failed_pickup.py` が期限後なら止まるようにする）。

## 5. 確かめ方（実装するとき）
- テスト: 対象にする異常・しない異常の分け方、1レース1回まで、上限の12レース、期限後に止まる、前の採点の書き出しに失敗したら取り直さない、ページが前の実行のものを置き換えない、軸の記録が変わらない。
- 本番の前に: 本番とは別のフォルダで、取得異常のあったレースを1日分（上限の範囲で）取り直し、ページ・採点・記録を確かめる。取るページの一覧と最大数は、取る前に決めて書く。
- 本番の後に: 取り直したレースの件数、異常の種類ごとの件数（直った・直らない）、かかった時間とアクセス数。

## 6. 決めてほしいこと（2026-11-13 時点の案。回答は7章）
1. 対象にする異常（1章の表）でよいか。
2. 取り直しの時刻（22:30 に1回）・回数（1レース1回）・上限（1回12レース）でよいか。cron に1行足してよいか。
3. 前の採点を `pickup_reruns/` に書き出す方法でよいか。
4. 軸の再検証に取り直した採点を入れない（案）でよいか。
5. 本番の v5.2 の採点（11/14〜）で取得異常の件数を数週見てから、実装するかどうかを決める、という順番にするか（件数が少なければ、取り直しを作らない判断もあり得る）。

## 7. 2026-11-13 外部レビューの回答
1. 対象の分け方はおおむね賛成。ページの保存の失敗は、まず保存の環境を直す対象（1章を直した）。
2. 22:30・1回・最大12レースは暫定案としてよい。12レースはアクセス数の上限ではないので、馬ページ・中間ページ・再試行を含む上限を決める（2章に足した）。cron への追加はまだ行わない。
3. 前の採点を保存してから置き換える案は賛成。期限をまたいだ場合は元の採点を置き換えない（3章に足した）。
4. 軸の評価に取り直しを入れない案は賛成。ただし、復元でも最初の採点を使う仕組みが要る（4章に足した）。
5. 数週の観察を先に行い、件数・異常の種類を見て実装の要否を決める。
- 観察で見るもの（成績は見ない）: 開催日ごとの v5.2 の採点のレース数、3項目の取得異常・ページの保存の失敗のあったレース数、異常の種類ごとの件数（1章の表の「する」「しない」別）、重賞かどうか。
