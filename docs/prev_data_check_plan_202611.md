## 1. 前走データの取り方（コードで確認した事実）

### 取得
- 取得元は db.netkeiba の馬ページの `table.db_h_race_results`。
- 行の日付（添字0）が対象日より前の最初の行を選び、`td` の一覧を添字で読む（添字は0から数える）。
  - 添字0: 日付（`prev_date`）、添字10: 人気（`prev_pop`）、添字11: 着順（`prev_rank`）、添字14: 距離（`prev_dist`）
  - 添字20: 指数（`prev_idx`。採点に使う）、添字21: `prev_idx_m`（何の値かは未確認）
- 見出しの名前は、保存済みのデータからは分からない。実ページで確かめるまで、添字20・21の意味はタスク1の対象として残す。

### キャッシュと保存
- 取った値は `output/horse_db.json` に入れる。**馬IDごとに1件**で、別の対象日のために取った値で上書きされる。
- `run_pickup_all.py`（`run.sh` から前日に実行）は、採点の実行が終わった後に、その日の出走馬のキャッシュの写しを `output/{日}/prev_data.json` に保存する（2026-06-11 のコミット 8d3cd2a から）。
  - `rerun_failed_pickup.py` は、既にある写しを優先してまとめて保存する。
- `scrape_prev_data.py`（結果の取得後に使う別の処理）も同じファイルを書く。2026-11-03 時点で `run.sh` と cron からは呼ばれていない。

### キャッシュを使う条件（判定式）
- `run_pickup_all.py`: `abs(対象日 − 取得日) ≤ 28日` かつ `前走日 < 対象日`。
  - 絶対値なので、**対象日より後に取った値も通る**。
  - 候補（3指数すべてでトップ3）は、条件を満たさなければ馬ページを取り直す。
  - 候補以外の馬は取り直さない。前走指数レース内1位の比較相手には、`前走日 < 対象日` だけを確かめて使う（取得日を見ない）。
- `scrape_prev_data.py`: `abs(対象日 − 取得日) ≤ 7日` かつ `前走日 < 対象日`。

### 前走の値を使う加点（`race_pickup.py`・現行 v5）
- 前走指数90以上 +2、70〜89 +1
- 前走指数レース内1位 +2。前走指数の加点との合計は上限3点
- 中4週以内（前走から28日以内）+2
- 前走好走（前走1〜6番人気かつ1〜3着）+2
- 同距離前走（±50m）+1

## 2. 確かめたい問題

1. **古い前走**: キャッシュの前走が、実際の前走より前のレースを指すことがある。
   - 例: 馬が4/5に走り、前日に取った値の前走は「4/5より前のレース」になる。3週後の4/26に再び走ると、キャッシュは条件を満たすので取り直さず、前々走を前走として使う。
2. **「**」で数字が無い**: 馬ページの指数が「**」で、前走指数の加点と、レース内1位の比較から外れる。
   - **「**」とログインの関係は仮説にとどめる。** 2026-06-17 に `scrape_prev_data.py` のログイン確認をやめた（コミット 2c952a5）が、確認をやめたことと、ログインしていない状態になったことは同じではない。
3. **レース内1位の比較相手**: 候補自身の前走が正しくても、比較相手に古い値や「**」があると、1位の判定が変わり得る。
4. **値そのもの**: 添字20の値が、指数の表（speed.html）の「前走」の列と合わない馬がいる（下調べでは1,877頭中97頭）。

## 3. 対象と使うファイル

- **期間**: 2026-03-21〜2026-11-01 のうち、`output/{日}/prev_data.json` がある日。
  - 期間は2つに分けて、別々に報告する。
    - **2026-06-13 以降**: `prev_data.json` が `run_pickup_all.py` の採点後の写しである見込みが高い期間。採点入力の「**確認候補**」として扱う。
    - **2026-06-12 以前**: `prev_data.json` を後から書いた可能性がある期間。採点入力の証拠にしない。
  - 6/13 以降を「確認候補」とする理由と限界:
    - 確かめたのは、6/20・10/18・11/1 の3日分の git の履歴（前日の取得コミットで1回書かれただけ）と、今の実行設定だけ。全期間の保存経路は確定していない。
    - 数え直しの最初に、期間内の全日について `prev_data.json` を変更したコミットを一覧にし、前日の取得コミット以外で変わった日を報告する。そういう日は外さずに「保存経路の追加確認が必要」と分類し、別に件数を出す（コミット日時だけでは、実際の取得・採点の日時を確定できないため）。
- **使うファイル**:
  - `output/{日}/prev_data.json`、`output/{日}/pickup_scores.json`、`output/{日}.xlsx`（指数の表）
  - 結果: `output/{日}/race_results.json`（旧版。着順が数字でない馬を捨てていた）、`output/{日}/race_results_all.json`（取り直し。着順なしの馬を含む）、`output/{日}/race_nonfinishers.json`（2026-11-02〜）
  - 実行時に、使ったファイルの一覧と sha256 を保存する。結果の取り直しが途中なら、その時点の完了日数を記録する。
- **除外**: 各条件で外した件数を、理由別に報告する（例: 馬IDが無い、前走日が無い、結果ファイルが無い日）。

## 4. 数え方

### 4-1. 単位
- 「対象日・レース・馬ID」の組の延べ数で数える。同じ馬が複数の日に出てくれば別に数える。「頭」とは書かない。

### 4-2. 出走の判定
- 前走日より後かつ対象日より前に「出走」があるかで、前走が古いかを判定する。
- 出走として数えるのは、着順のある馬と、競走中止・失格の馬。
- 取消・除外は出走に数えない。
- 状態は、`race_results_all.json` の着順なしの記録（`others`）と `race_nonfinishers.json` で区別する。
- 旧版の `race_results.json` しか無い日は、取消・中止などが載っていない。その日に馬の行が無いことを「出走していない」とはしない。状態を判別できない記録は「未確認」とする。
- 使った結果の版（旧版か取り直しか）と、取り直しの範囲を、記録ごとに残す。

### 4-3. 古さの判定（3つに分ける）
| 分類 | 条件 |
|---|---|
| 古いことを確かめられた | 前走日と対象日の間に、4-2 の出走を確かめた |
| 保存した結果の範囲では古さを見つけなかった | 間の出走が見つからなかった。地方競馬や結果を取っていない日の出走はここに入るので、**正しい前走とは判定しない** |
| 判定できない | 馬ID・前走日が無い、間の日の出走の状態が「未確認」など |

### 4-4. 採点への影響（3段階に分ける）
1. **採点後の写しに古い値が残っていた件数**: 6/13 以降の候補で、写しの前走が「古いことを確かめられた」もの。
   - 写しは採点の後に書かれる。採点中のキャッシュの更新と参照の順序を、コードで確かめるまでは「古い入力を使った件数」とは書かない。
   - 6/12 以前は「後から保存したデータで古さを見つけた件数（採点への影響は未確認）」として別に出す。
2. **合計点が変わる件数**: 正しい前走で加点を計算し直し、前走指数の合計上限3点を当てはめた後の差。
   - 正しい前走やその指数を確かめられないものは「**算定不能**」とし、「変化なし」にしない。
   - 後から取った値での計算は、「当時取れた情報の再現」とは区別して書く。
3. **★の段階・🔥・候補の順位が変わる件数**: 2 の結果から数える。

- 対象日より後に取った値（取得日 > 対象日）で採点されたものは、別に数える。

### 4-5. 前走指数レース内1位
- 比較相手（候補以外を含む、取消・除外を除いた出走馬）に、古い値・「**」・値なしがあるレースの候補を、すべて調べる対象にする。
- 次の2つを分けて数える。
  - 全頭の値を確かめたうえでの1位
  - 確かめられた馬の中だけの1位
- 全頭の値がそろわないときに1位の加点を認めるかは、ユーザーが決める。決まるまでは、どちらの扱いでも件数を出す。

### 4-6. 「**」
- 期間別・日別に、候補と比較相手のそれぞれで件数を出す。
- 原因は、実ページで確かめるまで書かない（2-2 のとおり仮説にとどめる）。

### 4-7. 添字20の値と指数の表の「前走」（下調べの97件）
- 値を比べる前に、同じものを比べているかを確かめる。
- 明細に並べる項目:
  - 対象レース（日・レース・レースID）と、前走レース（日・レース・分かればレースID）を別々に記録する
  - 馬ID
  - 両方の前走日。指数の表の側は前走日が出ないので、自前の結果から分かるときだけ書き、分からなければ「不明」とする。推測で埋めない
  - 元の文字（「*」付き、「**」、空を含む）と、数字にした値
  - 取得日
- 指数の表の値は、末尾の「*」（5走分のデータが無い印。`docs/data_sources.md`）を除いた数字を使う。200以上は隠し値（1000＋指数）を読んだ旧データなので比べない。どちらも件数を出す。
- 不一致が期間や形式に偏るかを見る。
- 一致率は、列の意味が正しいことの証明にはしない。

## 6. この計画の後に決めること（今回は承認の対象外）
- 直し方の案（コードを変えるので、案として出し、実装の前に同意を得る）:
  - 馬ページの履歴から「対象日より前の最新のレース」を選ぶ。
  - 採点の入力を、対象日・馬IDごとに、取得日時と選んだ前走のレースと一緒に保存する。
  - 別の対象日に値を使い回すときは、履歴を取り直す必要があるかを判断する。自前の結果で出走が見つからないことは、出走していない証拠にしない。
  - 前走指数レース内1位の比較相手にも、候補と同じ条件を当てはめる。
  - 当面は、対象日ごとに必要な馬を1回取り、その日の再実行では保存した値を使う方式が説明しやすい。
- 実ページで確かめること（netkeiba へのアクセス。結果の取り直しが終わってから）: 添字20・21の見出し、「**」が出る条件。
