# 脚質（horse_style.json）の更新の仕組みと記録の計画（2026-11-12 作成。2026-11-12 承認。外部レビュー3回を反映）

経緯: 残りのタスク「脚質の作り直し」。軸の再検証の計画（`docs/axis_recheck_plan_202611.md` 4.3）で、正式な評価の開始の条件の1つにした（脚質の更新の仕組みと記録、更新の規則）。外部レビュー（2026-11-12）の指示: 採点に使った脚質のファイルそのものを保存し、作成コードの版・入力の一覧とハッシュ・入力の対象期間を残す。更新の頻度と締切、評価中の更新をやり直しの対象にするかを先に決める。

この計画は、データの作り方と記録の仕方を決めるもので、成績の評価ではない。成績（脚質の加点の当たり外れ）は見ない。

## 1. 今の状態（2026-11-12 にコードと保存ファイルで確かめた）

### 1.1 使われ方
- 採点の「逃げ馬」（+1点）だけに使う（`race_pickup.score_horses`）。条件: 予測ペースが S（スロー）、`horse_style.json` のその馬の `style` が「逃げ」、`n_races` が2以上。
- `run_pickup_all.load_horse_style()` が `output/horse_style.json` を読み、`rerun_failed_pickup.py` も同じ関数で読む。採点の記録（`pickup_scores.json` の `quality`）には、どの脚質のファイルを使ったかが残らない。

### 1.2 作り方（`build_horse_style.py`。手で動かしたときだけ）
- `output/` の全日付の `race_results.json` を読み、各馬の最初の通過順の位置から相対位置 `(位置−1)÷(頭数−1)` を出し、馬ごとの平均で分類する（逃げ 0〜0.15、先行 0.15〜0.35、差し 0.35〜0.60、追い込み 0.60〜）。頭数が8未満のレースは使わない。
- 対象日の区別は無い（その時点にある全部の結果を使う）。作った日時・入力・作成コードの版は記録しない。`output/horse_style.json` を上書きする。
- 最後に作ったのは 2026-06-14（git の記録）。6255頭（逃げ 1037・先行 1288・差し 1678・追い込み 2252、2走以上 3317頭）。

### 1.3 入力の問題
1. **採点したレースだけの結果から作っている**: `race_results.json` は採点したレース（候補がいたレース）だけ（例: 2026-11-01 は全24レース中8レース）。脚質は、候補がいたレースに偏った一部の出走から作られる。全レースの結果（`race_results_all.json`。取消・中止などの `others` を含む）は 2025-09-20〜2026-11-01 の122日分あるが、`rescrape_results_full.py` を手で動かしたときだけ作られる。
2. **頭数に、着順の無い馬が入っていない**: 割る頭数は `race_results.json` の馬の数（着順のある馬だけ）。通過順の位置は、途中で中止した馬も含めた位置なので、位置が頭数より大きい例が27件ある（124日・23,550頭）。
3. **通過順の欠け**: 23,550頭中、通過順があるのは14,549頭。結果を取った当日の夜は通過順が空のことがある（CLAUDE.md の「3. レース結果を保存」）。後日取り直すと、同じ日の入力が変わる。
4. **6/14 より後の結果が入っていない**: その後の45日分の結果が脚質に入っていない。その間に初めて走った馬などは脚質が無い。
5. **着順の無い馬の通過順が保存されていない**: `race_results_all.json` の `others`（中止206・除外116・取消66頭）には通過順の項目が無い。中止の馬が最初の通過地点を通ったかどうかは、今の保存からは分からない。
6. 直線のレース（新潟の芝1000m）は、通過順の値が1つ（4レースで確認）。全馬の通過順が空のレースは、全レースの取り直し（122日）に無かった。値が1つあることだけでは、その値がコーナーの通過順と同じ意味の位置かは分からない（何の地点の位置かは確かめていない）。

## 2. 決めること（案。2026-11-12 外部レビュー3回目まで反映）

### 2.1 入力（全レースの結果。外部レビューの推奨は案A）
- 案A（勧める）: **全レースの結果**を使う。毎日の結果の取得（`scrape_results.py`）で、採点したレースに加えて全レースの着順・通過順と、着順の無い馬（取消・除外・中止・失格）を同じ取得で保存する（取得するページが1日 8〜19 から 24〜36 レースに増える）。着順の無い馬の通過順も、ページにあれば保存する。過去は `race_results_all.json` を使う。
- 全レースがそろったかは、件数ではなく、**その日の予定のレースIDの一覧**（レース一覧のページ・カレンダー）と照合して確かめる。そろわない日は、その日を入力に使わず、理由を記録する（採点したレースだけの結果で代わりにしない）。
- 一部の取得に失敗したファイルで、保存済みの完全な結果を上書きしない（取り直しは、完全にそろったときだけ置き換える）。
  - **2026-11-12 変更（設計への外部レビューを受けて。ユーザー承認）**: 「完全にそろったときだけ置き換える」から、**レースごとに置き換える**方式に変えた。理由: 1レースの失敗で、その回に取れた他のレースの更新（通過順の取り直しなど）まで捨てずに済み、レースごとの取得日時で古い値が残っていることを追えるため。元の規則は上に残す。変更後の規則:
    - 今回取れたレースだけを置き換え、取れなかったレースは前に保存した値を残す（消さない・空にしない）。
    - `complete` は、今回の取得が成功したことではなく、**保存済みのデータのレースの集合が予定の一覧とそろっている**ことを表す。
    - 今回の取得の失敗は、`complete: true` でも取得の記録（`results_fetch_log.json`）と通知に残す。
    - 1レースの着順・着順の無い馬・レースの条件は、同じ取得の結果を一組として置き換える（一部だけ新しくしない）。
    - 形の異常があるページ（成績の表が無い・通過順のセルが無いなど）は「取得の成功」とせず、正常な前の値に上書きしない。
- 案B: 今のまま `race_results.json`（採点したレースだけ）を使う。取得は増えないが、偏りが大きい。
- 案Aでも、2.2 の規則で使えるレースだけを使うので、**偏りは残る**（通過順がそろわないレース・中止のあるレースが外れる）。「全レースから取るので偏りが無くなる」とは扱わない。

### 2.2 頭数と通過順（使うレースの規則と、使わない理由）
- 割る頭数は、発走した頭数（着順のある馬＋競走中止＋失格。取消・除外は入れない）。
- **発走した全馬の最初の通過順を確かめられるレースだけ**を使う（保守的な規則）。使わないレースは、理由を分けて件数を記録する:
  1. 通過順がまだ取れていない（着順のある馬の通過順が空。結果を取った当日の夜など）
  2. 中止などで、通過順が無い・確かめられない馬がいる（中止の馬の通過順の保存が無い今の過去分は、中止のあるレースはすべてこれ）
  3. 通過順を分類に使えない形のレース（数字の並びでない、など）。直線のレースは、その1つの値が何の地点の位置かを実ページ・公式の説明で確かめるまで、ここに入れて使わない
  4. 状態が分からない馬がいる・頭数が合わない・値が範囲外（1〜発走した頭数の外）・同じ馬が2回いる
  5. 頭数が8未満（今の規則のまま）
- 脚質の `n_races` は、総出走数ではなく、**分類に使えた出走の数**とする（名前は変えずに、意味を記録に書く）。
- 分類の境目（0.15・0.35・0.60）と、採点の「2走以上」は変えない（点数の式に関わるので、この計画では変えない）。

### 2.3 作る時点と入力の確定
- 脚質は、対象日ごとに、**対象日の前日より前の開催日の結果だけ**で作る（日付で決める。結果の取得の時刻に頼らない）。例: 日曜の対象日には土曜の結果を入れない（手で土曜の結果を早く取っても、遅く再実行しても同じ）。月曜が祝日の開催なら、土曜までの結果を使い、日曜は入れない。
- 作るのは採点の前（`run.sh` の中で、`run_pickup_all.py` の前）。期限は対象日 00:00（日本時間）で、**作り終えた時刻が対象日 00:00 以上なら使わない**（00:00 ちょうども使わない。前走データと同じ境界）。
- **入力の確定**: 作り始めに、基準にする commit の ID（`HEAD`）を1つ固定し、入力はその commit の blob から読む（作業ファイルを読まない。確かめた後に作業ファイルが変わっても入力は変わらない）。入力にする各ファイルが、その commit にあり、作業ファイルと同じ（commit されていない変更が無い）ことも確かめる（違えば作らない。2.5）。記録に、基準の commit の ID、入力を確定した日時、各入力のファイル名・SHA-256・git の blob ID、作成コードの版を残す。固定した入力は、基準の commit から取り出せる。
- 後から補完された結果（通過順の取り直しなど）は、次の対象日の脚質から反映する。保存した脚質と、その入力の記録は書き換えない。

### 2.4 保存（2段階: 対象日用の全体を先に固定し、採点時に出走馬へ結び付ける）
採点するレースの全出走馬は、採点の中でレースごとに取る出馬表（`run_pickup_all.score_race` の `scrape_shutuba`）で初めて分かる。候補の CSV だけでは全出走馬を特定できない。そこで2段階に分ける。

1. **対象日用の脚質の全体**（採点の前に作って固定する）: 2.2・2.3 の規則で、過去の結果から全馬の脚質を計算する。`output/{対象日}/horse_style/{実行ID}.json` に保存する。中身:
   - 全馬の脚質（`style`・`n_races`・平均の相対位置）。
   - 作成コードの版（`STYLE_BUILD_VERSION`）、作った日時、入力を確定した日時、基準の commit の ID。
   - 入力の一覧（2.3）と対象期間（最初と最後の開催日）、使ったレース数、使わなかったレース数（2.2 の理由別）、全レースがそろわず使わなかった日。
   - 全体は **git に入れる**（今の `horse_style.json` は 555KB）。後から採点し直したレース・追加されたレースの馬の脚質も、この全体から取り出せるようにするため。全体のハッシュだけを残して中身を復元できない形にはしない。
2. **レースごとの結び付け**（採点の中、点数を計算する前）: 出馬表の全馬（取消・除外を除く）を馬IDで全体に結び付け、状態を付けて、そのレースの採点の記録に保存してから点数を計算する。状態は「脚質あり」「分類に使えた出走が1走（採点の加点の対象外）」「脚質なし（分類に使えた出走が無い。正常な履歴不足）」。馬IDが無い馬は、前走データと同じく馬IDの問題として扱う。
- 採点の記録（`pickup_scores.json` の各レースの `quality`）に、使った全体の参照（実行ID・SHA-256・作成コードの版）を入れる。
- 同じ日の再実行・部分の再実行（`rerun_failed_pickup.py`）は、固定した同じ全体を使って結び付け直す（2.6）。
- `output/horse_style.json` は書き換えない（研究用のスクリプト4つと停止中の `rescore.py` が読む古いファイルとして残す）。採点はこれを読まなくなる。

### 2.5 作れないとき（正常な履歴不足と分ける）
- 次は「作成失敗」とし、採点は続けるが、その日の全レースを品質の問題（「脚質を作れない」）にする（買い目なし・🔥なし。軸の記録は品質の問題による軸なし。2.8）。前回の脚質で代わりにしない。
- 作成失敗も記録を残す: `output/{対象日}/horse_style/{実行ID}.json` に、状態「作成失敗」、失敗した日時、作成コードの版、基準の commit の ID（決まっていれば）、理由を書く（git に入れる）。採点の記録の `quality` は、この失敗の記録を参照する。
- 失敗の記録の保存そのものに失敗した場合は、「明示的な作成失敗」として扱わない。記録の欠けとして扱い（2.8 の「記録できない」）、`run.sh` の出力の印と LINE で知らせる経路を設計に入れる。
  - 入力を読めない、入力が基準の commit に無い・作業ファイルと違う、保存できない、作り終えた時刻が対象日 00:00 以上
  - 使えたレースが0件（全入力が欠けて空の脚質になった場合を「作成成功」にしない）
- 個々の馬に脚質が無いのは、正常な履歴不足（2.4 の「脚質なし」）で、品質の問題にしない。

### 2.6 同じ日の再実行（毎回作るのではなく、その日の最初の成功で確定する）
- 対象日ごとに、**最初に作成・保存に成功した記録で、その日の脚質を確定する**（失敗の記録では確定しない）。同じ日の通常の再実行（`run.sh` のやり直し）と部分の再実行（`rerun_failed_pickup.py`）は、その記録を使い、作り直さない。入力が後で更新されても、その日の脚質は差し替えない。
- 作成失敗（2.5）の後は、期限（対象日 00:00 より前）までなら作り直してよい。最初に作成に成功して保存した時点で確定し、以後は変えない。失敗の記録は消さずに残す。
- 作り直しに成功しても、失敗の記録を参照して**すでに保存した軸の記録は書き換えない**（軸の記録の「書き換えない」規則。`docs/axis_record_design_202611.md` 2.4）。成功した脚質で採点し直しても、軸の記録をし直すと入力が違うので止まり、通知される（後からの `rerun_failed_pickup.py` と同じ扱い）。
- 同じ日の作成は、ロック（前走データと同じ `fcntl.flock`）を持って行い、記録は一時ファイルに書いてから置き換える（書きかけの記録を残さない）。確定した記録がすでにあれば、作らずにそれを使う。
- 記録が無いのに部分の再実行をした場合は、止まる。

### 2.7 評価中の更新の扱い（軸の再検証との関係）
- 決まった規則（2.1〜2.6、作成コードの版が同じ）のままの毎日の作成は、入力が増えるだけなので、評価のやり直しの対象にしない。後から補完された結果（通過順の取り直しなど）が次の対象日から入るのも、この規則の中の更新として扱い、各日の記録の入力の一覧に残る。これを軸の計画書 4.3 の分類の例として書く。
- 作成の規則・入力の選び方の変更（入力の範囲、頭数・通過順の規則、分類の境目、対象日・入力の確定の規則）は、作成コードの版を上げ、「影響あり」として軸の計画書 4.3 の規則に従う（入れる前に分類し、正式な評価の期間中なら選ぶ期間からやり直す）。
- 規則の外の作り直し（手で動かす、別の入力で作る）は、評価の期間中はしない。

### 2.8 軸の記録への通し方
- `quality` に参照を書くだけでなく、`axis_record.py` の入力の保存・同じ入力かどうかの判定（`input_key`）・記録の復元で、その日の脚質の記録が、ある・JSON として読める・対象日が合う・SHA-256 が `quality` の参照と合う、を確かめる。状態ごとの扱い:
  - **作成成功**の記録があり、確かめが通る: 通常どおり記録する。
  - **作成失敗**が明示的に記録されている（失敗の日時・版・理由がそろい、`quality` の参照と合う）: 品質の問題による軸なしとして記録する（記録の欠けではない）。
  - 作成成功と参照されているのに、ファイルが無い・読めない・SHA-256 が違う: そのレースは記録できない（前走データの記録と同じ扱い）。
  - 成功・失敗のどちらの記録も無い（参照が無い）: 記録できない。
- 記録できないものは、記録の欠けとして `axis_record.py check` が知らせる。
- 復元（期限後に、確定した入力で計算し直す）でも、期限前に push された commit にある脚質の記録だけを使う。

## 3. 実装の範囲（設計は docs/horse_style_design_202611.md。実装の前に別に説明して同意を得る）
- `scrape_results.py`: 全レースの結果と着順の無い馬（通過順を含む）の保存、予定のレースIDとの照合、一部失敗で完全な結果を上書きしない。
- `build_horse_style.py`: 対象日・入力の一覧を受け取り、2.2 の規則と理由別の件数を返す関数にする（今の作り方の版も呼べるように残す）。
- `run.sh`・`run_pickup_all.py`・`rerun_failed_pickup.py`: その日の全体の作成・確定・読み直し（ロックと原子的な保存）、レースごとの出走馬への結び付けと保存（2.4）、作成失敗の記録。
- `data_quality.race_quality_issues`: 脚質の記録が無い・版が違う・作成失敗。
- `axis_record.py`: 2.8。
- テスト: 前日以前の結果だけを使う（手で早く取った前日の結果も入らない）、作り終えた時刻が対象日 00:00 ちょうどなら使わない、頭数の数え方と理由別の除外（直線のレースを含む）、範囲外・重複、同じ日の再実行で同じ全体を使う、部分の再実行で追加したレースの馬も同じ全体から結び付く、作成失敗の後の作り直しと確定（失敗の記録が残り、保存済みの軸の記録は書き換えない）、空の脚質を成功にしない、commit されていない入力で作らない、基準の commit の blob から読む（確かめた後に作業ファイルを変えても入力が変わらない）、軸の記録での状態ごとの扱い（成功・明示的な失敗・ファイルが無い／ハッシュ違い・記録が無い）。
- 設計の段階で確かめること（成績は見ない）:
  1. 本番と同じ入力の状態（cron の結果の取得と commit の後、`run.sh` の前）で、commit 済みの条件を満たして作れるか。結果の取得の commit が無い日・失敗した日にどうなるか。
  2. 新しい規則で使える日数・レース数・出走数、使わないレースの理由別の件数、11/7・11/8 の出走馬の状態別の件数（脚質あり・1走・脚質なし）。件数だけを調べ、成績は集計しない。
  3. 全レースの取得の量と所要時間を、限定した試行で測る。取得の失敗・アクセス制限のときに止める条件を決める。
  4. 結果のページに中止の馬の通過順が出るか（出なければ、中止のあるレースは使わないまま）。直線のレースの値の意味（確かめられるまで使わない）。
  5. git の容量の実際の増え方を測る（圧縮で小さくなるのは今は見込み）。
- 1〜5 は本番に入れる前に確かめる。
- 実データでの確かめ: 2026-11-07・11-08 を対象日にして作り、今の `horse_style.json` と逃げの馬の数・違いの理由を比べる。**これは「今保存されている過去の結果による作り直し」で、当時の脚質の再現ではない**（その後に補完された結果が入る）と区別して報告する。成績は見ない。

## 4. 決めてほしいこと（2026-11-12、7項目ともユーザーが承認）
1. 入力を全レースの結果にする（案A。外部レビューの推奨）。取得が増える。
2. 頭数・通過順の規則と、使わない理由の分け方（2.2）。中止のある過去のレースと、確かめるまでの直線のレースは使わないことになる。
3. 対象日の前日より前の結果だけで、採点の前に作る。基準の commit を固定してその blob から読み、作り終えた時刻が対象日 00:00 以上なら使わない（2.3）。
4. 対象日用の全体を先に固定して git に入れ、採点の中でレースごとに出馬表の全馬へ状態付きで結び付ける（2.4）。
5. 作成失敗と正常な履歴不足を分け、作成失敗は記録を残して品質の問題にする（2.5）。
6. 同じ日は、その日の最初に作成・保存に成功した記録を使う（2.6。失敗の記録は別に残す）。
7. 評価中の更新の扱い（2.7）と、軸の記録への通し方（2.8。明示的な作成失敗は品質の問題による軸なし、記録やファイルの欠けは記録できない）。
