# 脚質（horse_style.json）の更新の仕組みと記録の計画（2026-11-12 作成。未承認の案）

経緯: 残りのタスク「脚質の作り直し」。軸の再検証の計画（`docs/axis_recheck_plan_202611.md` 4.3）で、正式な評価の開始の条件の1つにした（脚質の更新の仕組みと記録、更新の規則）。外部レビュー（2026-11-12）の指示: 採点に使った脚質のファイルそのものを保存し、作成コードの版・入力の一覧とハッシュ・入力の対象期間を残す。更新の頻度と締切、評価中の更新をやり直しの対象にするかを先に決める。

この計画は、データの作り方と記録の仕方を決めるもので、成績の評価ではない。成績（脚質の加点の当たり外れ）は見ない。

## 1. 今の状態（2026-11-12 にコードと保存ファイルで確かめた）

### 1.1 使われ方
- 採点の「逃げ馬」（+1点）だけに使う（`race_pickup.score_horses`）。条件: 予測ペースが S（スロー）、`horse_style.json` のその馬の `style` が「逃げ」、`n_races` が2以上。
- `run_pickup_all.load_horse_style()` が `output/horse_style.json` を読み、`rerun_failed_pickup.py` も同じ関数で読む。採点の記録（`pickup_scores.json` の `quality`）には、どの脚質のファイルを使ったかが残らない。

### 1.2 作り方（`build_horse_style.py`。手で動かしたときだけ）
- `output/` の全日付の `race_results.json` を読み、各馬の最初の通過順の位置から相対位置 `(位置−1)÷(頭数−1)` を出し、馬ごとの平均で分類する（逃げ 0〜0.15、先行 0.15〜0.35、差し 0.35〜0.60、追い込み 0.60〜）。頭数が8未満のレースは使わない。
- 対象日の区別は無い（その時点にある全部の結果を使う）。作った日時・入力・作成コードの版は記録しない。`output/horse_style.json` を上書きする。
- 最後に作ったのは 2026-06-14（git の記録）。6255頭（逃げ 1037・先行 1288・差し 1678・追い込み 2252、2走以上 3317頭）。

### 1.3 入力の問題
1. **採点したレースだけの結果から作っている**: `race_results.json` は採点したレース（候補がいたレース）だけ（例: 2026-11-01 は全24レース中8レース）。脚質は、候補がいたレースに偏った一部の出走から作られる。全レースの結果（`race_results_all.json`。取消・中止などの `others` を含む）は 2025-09-20〜2026-11-01 の122日分あるが、`rescrape_results_full.py` を手で動かしたときだけ作られる。
2. **頭数に、着順の無い馬が入っていない**: 割る頭数は `race_results.json` の馬の数（着順のある馬だけ）。通過順の位置は、途中で中止した馬も含めた位置なので、位置が頭数より大きい例が27件ある（124日・23,550頭）。
3. **通過順の欠け**: 23,550頭中、通過順があるのは14,549頭。結果を取った当日の夜は通過順が空のことがある（CLAUDE.md の「3. レース結果を保存」）。後日取り直すと、同じ日の入力が変わる。
4. **6/14 より後の結果が入っていない**: その後の45日分の結果が脚質に入っていない。その間に初めて走った馬などは脚質が無い。

## 2. 決めること（案）

### 2.1 入力（どの結果を使うか）
- 案A（勧める）: **全レースの結果**を使う。毎日の結果の取得（`scrape_results.py`）で、採点したレースに加えて全レースの着順・通過順・着順の無い馬を保存するようにする（取得するページが1日 8〜19 から 24〜36 レースに増える）。過去は `race_results_all.json` を使う。全レースの結果がそろわない日は、その日を入力に使わず、理由を記録する（採点したレースだけの結果で代わりにしない）。
- 案B: 今のまま `race_results.json`（採点したレースだけ）を使う。取得は増えないが、偏りが残る。
- 判断の材料: 案Aは netkeiba への取得が増える（利用規約上グレーで、低頻度の範囲で使う決まり。CLAUDE.md）。案Bは、どの馬に脚質が付くかが、その馬が候補のいるレースに出たかどうかで決まる。

### 2.2 頭数と通過順
- 割る頭数は、発走した頭数（着順のある馬＋競走中止＋失格。取消・除外は入れない）にする。着順の無い馬の状態が分からないレースは使わない（推定しない）。
- 通過順は、そのレースで発走した全馬の通過順がそろっているレースだけを使う。一部の馬だけ空のレースは使わず、件数を記録する。
- 分類の境目（0.15・0.35・0.60）、頭数8未満を使わない、採点の「2走以上」は変えない（点数の式に関わるので、この計画では変えない）。

### 2.3 対象日（その時点で知り得た結果だけ）
- 脚質は、対象日ごとに、**対象日より前の開催日の結果だけ**で作る。対象日以後の結果は入れない（過去の作り直しにも同じ関数を使えるようにする）。
- 作るのは採点の前（`run.sh` の中で、`run_pickup_all.py` の前）。前日 17:00 の採点では、その日（土曜など）の結果はまだ無い（結果の取得は 18:30）。そのため、日曜の採点には土曜の結果が入らない。これを規則として受け入れる。
- 入力の期限: 対象日 00:00（日本時間）より前に作り終えたものだけを使う（前走データと同じ）。

### 2.4 保存（採点に使った脚質そのもの）
- 作るたびに、`output/{対象日}/horse_style/{実行ID}.json` に保存する（git に入れる）。中身:
  - 脚質（その日に採点するレースに出る全馬の分。全馬の脚質は大きいので、出走馬に絞る。絞る前の全体のハッシュも残す）
  - 作成コードの版（`STYLE_BUILD_VERSION`）、作った日時、作成時の git の commit
  - 入力の一覧（日付・ファイル名・SHA-256・使ったレース数・使わなかったレース数と理由別の件数）と、入力の対象期間（最初と最後の開催日）
- 採点の記録（`pickup_scores.json` の各レースの `quality`）に、使った脚質の記録（実行ID・SHA-256・作成コードの版）を入れる。
- 同じ日の `rerun_failed_pickup.py` は、作り直さず、その日の記録を使う（同じ日に違う脚質で採点しない）。記録が無ければ止まる。
- `output/horse_style.json` は書き換えない（研究用のスクリプトが読む古いファイルとして残す）。採点はこれを読まなくなる。

### 2.5 作れないとき
- 脚質を作れない（入力を読めない・保存できない）ときは、採点は続けるが、その日の全レースを品質の問題（「脚質を作れない」）にする（買い目なし・🔥なし。軸の記録は品質の問題による軸なし）。前回の脚質で代わりにしない。

### 2.6 更新の頻度と締切
- 頻度: 採点のたびに自動で作る（手で作り直す運用はやめる）。締切は 2.3 の入力の期限。
- 結果の取り直し（通過順の補完など）で過去の結果ファイルが変わったら、次に作る脚質から反映される。すでに保存した脚質は書き換えない。

### 2.7 評価中の更新の扱い（軸の再検証との関係）
- 決まった規則（2.1〜2.6、作成コードの版が同じ）のままの毎回の作り直しは、入力が増えるだけなので、評価のやり直しの対象にしない。これを軸の計画書 4.3 の分類の例として書く。
- 作成コードの版が変わる変更（入力・頭数・通過順・分類の境目・対象日の規則の変更）は、「影響あり」として軸の計画書 4.3 の規則に従う（入れる前に分類し、正式な評価の期間中なら選ぶ期間からやり直す）。
- 規則の外の作り直し（手で動かす、別の入力で作る）は、評価の期間中はしない。

## 3. 実装の範囲（承認の後に、別に説明して同意を得る）
- `build_horse_style.py` を、対象日・入力の一覧を受け取る関数にする（今の作り方の版も呼べるように残す）。
- `run.sh` に作る手順を足し、`run_pickup_all.py`・`rerun_failed_pickup.py` が、その日の記録を読むようにする。
- `data_quality.race_quality_issues` に、脚質の記録が無い・版が違う、を足す。
- 案Aなら、`scrape_results.py` の取得の範囲を広げる（取得の量が増える）。
- テスト: 対象日以後の結果が入らない、頭数の数え方、通過順の欠けのレースを使わない、保存と再実行での読み直し、作れないときの品質の問題。
- 実データでの確かめ: 2026-11-07・11-08 を対象日にして作り、今の `horse_style.json` と、逃げの馬の数・違いの理由を比べる（成績は見ない）。

## 4. 決めてほしいこと
1. 入力を全レースの結果にするか（案A）、今の採点したレースだけにするか（案B）。案Aは取得が増える。
2. 頭数・通過順の扱い（2.2）。直すと、作成コードの版が上がる。
3. 対象日より前の結果だけで、採点の前に作る（2.3）。日曜の採点に土曜の結果が入らないことを受け入れるか。
4. 保存の仕方（2.4）。出走馬に絞った脚質を git に入れる。
5. 作れないときに品質の問題にする（2.5）。
6. 評価中の更新の扱い（2.7）。
