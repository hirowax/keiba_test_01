## 3. A3: 時点整合性

### 3-1. 【重大】shutuba 取得が8頭で打ち切られ、スコアに馬番バイアスがある

`odds_map` / `pop_map` / `horse_id_map` が全レースで**ちょうど8件**。欠損は常に馬番9以上。

| horse_id_map の件数 | レース数 |
|---|---|
| 0件 | 424 |
| 6件 | 4 |
| 7件 | 12 |
| **8件** | **1,175** |

馬IDがないと前走データ（`prev_data` / `horse_db`）と脚質を引けない。結果:

| 候補馬 | 頭数 | 前走系ファクターが1つ以上付いた割合 |
|---|---|---|
| 馬番1〜8 | 1,503 | **83.2%** |
| 馬番9以上 | 674 | **17.1%** |

前走系は前走指数(+2)・前走指数レース内1位(+2)・中4週(+2)・前走好走(+2)・同距離(+1) で
最大9pt。つまり**馬番9以上の候補馬は構造的に最大9pt を得られない**。
これはスコア分布・閾値キャリブレーション・🔥選出のすべてに効く。

馬番9以上で17.1%が付いているのは、`rescore.py` が `race_results.json`（全頭）から
`horse_id_map` を補完するため。**再スコアした日だけバイアスが部分的に消える**ので、
`docs/ops_log_202610.md` の v5/v6 前後比較は、この差を含んだ比較になっていた可能性がある。

原因の切り分けは未了（lazy loading か `wait_until="domcontentloaded"` の取得タイミングか、
セレクタ `td.HorseInfo a[href*='/horse/']` の構造変化か）。実レースでの確認が必要なため、
読み取り専用の本段階では実施しない。診断手順は §5-1 に案として記載。

### 3-2. 証跡ラベル（日付単位）

| ラベル | 日数 | スナップショット | オッズ期 |
|---|---|---|---|
| 当時保存（前日以前に生成） | 32 | あり | あり |
| 当時保存（前日以前に生成） | 4 | あり | なし |
| 当時保存 / 再スコア済 | 18 | あり | なし |
| 当日生成（発走前後は不明） | 3 | あり | あり |
| 当日生成 / 再スコア済 | 5 | あり | なし |
| 遡及作成（対象日より後に生成） | 27 | **なし** | なし |
| 遡及作成 / 再スコア済 | 26 | なし | なし |
| 遡及作成 / 再スコア済 | 5 | あり | なし |

- **当時保存 54日 + 当日生成 8日 = 62日** が「当時の予想」として扱える上限
- **遡及作成 58日** は対象日より後に生成されている。既に観測済みの過去であり、未使用テストに使えない
- 予想生成時刻はファイル単位でしか残らず、発走予定時刻を保存していない。
  「当日生成」8日は発走前かどうか**時刻不明**として扱う
- **再スコア済 54日のうち18日は「当時保存」だった日**。再スコアで `scored` が上書きされているため、
  当時のスコアそのものは失われている（`generated_at` は保持されているので日付の証跡は残る）
