# 過去データの作り直しの手順を少数のレースで試す計画（タスク8。2026-11-07 作成・未承認）

**ページを取りに行く前に、この計画の承認を得る。成績は見ない（点数・入力値・候補・加点の内訳を、保存した記録と比べるだけ）。全期間の作り直しはしない。**

## 1. 目的
- 9/12 以降の過去のレースについて、今の採点（v5.1）の点数を、その日の時点で分かっていた値だけで作り直せるかを確かめる。
- 作り直した点数は、タスク10（🔥の基準）とペーパートレードの見直しの材料になる。今の過去の点数は、前走データが別の馬の値・古い値になっているので使えない（`docs/incident_umaban_20261030.md`）。
- 試しの結果を見せて承認を得てから、全期間の作り直しに進む（事故の文書のタスク8の条件）。

## 3. 試しのやり方
### 3.1 対象のレース（案）
- **対照（11/7 から2レース）**: 本番の入力の記録（`prev_inputs`）と点数がある日。後から同じ手順で作り直して、本番と同じになるかを見る。違いが出たら、後から取ったための違い（指数の修正・取消の扱いなど）か、手順の誤りかを1件ずつ調べる。
- **馬番の取り違えを直した後（10/31・11/1 から2レース）**: 出馬表の値（上位3頭など）は信頼できるが、前走データが古い可能性がある日。
- **直す前（9/12〜10/25 から2レース）**: すべての保存値が疑わしい日。
- レースは、候補がいる平地のレースから、日付ごとに番号の一番小さいものを選ぶ（成績を見て選ばない）。

### 3.2 手順
1. 指数の表から、新しい定義で候補を選ぶ（`scraper.find_triple_top5_rows`）。保存した候補と比べる。
2. 出走全馬の馬ページを取り、`prev_inputs.parse_results_table` に対象日を渡して前走を選ぶ。本番と同じ cookies・間隔。ページは `research/rebuild_trial_202611/` に保存する。
3. 通過順の履歴を、対象日より前の `race_results_all.json` だけから作る（`build_horse_style.py` の判定を呼ぶ。書き写さない）。
4. 上位3頭・ピックアップ・出走馬分析は、次の3つを並べて比べる（どれを使うかは試しの後に決める）。
   - (i) 保存値（`pickup_scores.json`）
   - (ii) 今、出馬表と data_top のページを取り直した値（レースの後でもその欄が残っているか）
   - (iii) この3項目を入れない点数
5. 点数は今の採点の関数（`race_pickup.score_horses`）を呼んで出す。書き写さない。
6. 比べるもの: 候補・各入力値・前走の行・レース内1位の判定・加点の内訳・合計点。保存した記録と、合計点だけでなく内訳まで並べる。

### 3.3 ページを取る量
- 6レース×約15頭＝約90の馬ページ、出馬表と data_top が12ページ。間隔は 6〜12秒で、約30分。
- 本番（毎日 17:00〜）と重ならない時間に行う。IP ブロックの画面が出たら止める。

### 3.4 出力
- `research/rebuild_trial_202611/` に、取ったページ・コード・作り直した入力と点数・比べた結果を置く。
- 過去の `pickup_scores.json`・`prev_data.json`・`paper_bets.json` などは書き換えない。

## 4. 前もって分かっている限界
- 馬ページの指数が、後から直されることがあるかは確かめていない。対照の11/7 で、本番の記録と後から取った値を比べて確かめる（2レース分だけ）。
- 取消を前日の時点で知っていたかは区別できない。結果の取消・除外の馬は採点から外す（本番は出馬表の取消の印で外している）。
- 上位3頭などの3項目は、読み方そのものが未確認（`docs/data_sources.md` の要確認2）。この試しでは確かめきれない。読み方の確認は別のタスクとして、明日以降の出馬表で実ページを保存して行う必要がある。
