## 基本方針：「私（Fable）ならどう買うか」

検証済みデータに基づく結論。**現時点で実銭を張って期待値プラスの買い方は存在しない**
（◎複勝ROI 69%・◎-○馬連27%・ワイド67%、単勝104.7%は外れ値依存）。よって：

1. **今は実銭を張らない**。買うなら娯楽予算と割り切った最小単位のみ
2. **「前向きペーパートレード」を仕組み化する**。毎週の◎/紐から事前登録した買い目メニューを機械生成し、
   JRA公式払戻で自動精算・累積集計する。バックテストと違い、未来情報リーク・多重検定・データ汚染が
   構造的に起こらないため、これが最も強い証拠になる
3. **90日経過後、事前登録基準を満たしたメニューだけ実銭に昇格**（固定ユニット・1点100円から）
4. **実際の馬券購入は常に人間が行う**（AIは購入を実行しない。判断材料の提示まで）

### 過去結果は見るべきか？

**用途を分けて使う：**
- 過去結果（バックテスト）の役割 = **ダメな買い方を殺すこと**。馬連・ワイドのベタ買いは過去データで
  既に殺した。これは有効な使い方
- **実銭投入の判断は前向き検証（ペーパートレード）でのみ行う**。このプロジェクトのバックテストは
  (a) horse_dbの時点汚染、(b) 検証の繰り返しによる多重検定、(c) 外れ値依存、の3リスクを完全には
  除去できないため、「過去で勝てた」は実銭の根拠にしない
- 精算に使う払戻データは**JRA公式（jra.go.jp）から取得**する（Issue #1）

### ペーパートレードの買い目メニュー（事前登録・変更禁止）

| メニュー | 買い目 | 1レースあたり | 過去実績（参考） |
|---|---|---|---|
| M1: ◎複勝 | 🔥馬の複勝1点 | 100円 | ROI 69%（負け筋の基準線） |
| M2: ◎単勝 | 🔥馬の単勝1点 | 100円 | ROI 105%（外れ値依存・要前向き確認） |
| M3: ◎-○ワイド | ○=スコア2位重複馬 or 単指数1位最上位 | 100円 | ROI 67%（負け筋の基準線） |
| M4: ◎軸3連複 | 紐=B∪D∪C から2頭流し C(k,2)点 | 平均630円 | 未検証（Issue #2で過去分、以後前向き） |
| M5: EVフィルター付き◎複勝 | M1のうち 損益分岐オッズ以上のみ | 0〜100円 | Phase B（2026-11）から追加 |

- 対象レース: ◎（スコア1位かつ8pt以上）が存在する全レース
- M1〜M4は毎週全レース機械記録。「調子が悪いから今週は外す」等の裁量は禁止
- 判定基準（90日後・メニューごと）: 回収率≥110% かつ 的中上位3本除外後≥80% かつ 的中数≥15
  → 満たしたメニューのみ実銭昇格を人間に提案する

## 運用ルール（モデル切替・レビュー・エスカレーション）

### 実装フロー
1. 人間が `/model` で担当モデルに切り替え、「Issue #N やって」と指示
   （各Issueは本ドキュメント＋参照先仕様だけで作業可能なように書いてある）
2. 担当モデルは **feature ブランチ**（`feat/issue-N-xxx`）で作業しコミット（pushは人間の指示待ち）
3. 人間が `/model claude-fable-5` に戻して「Issue #N レビューして」と指示
4. Fable は `git diff main..feat/issue-N-xxx` + 受入基準チェックリストでレビュー
   - **合格**: mainにマージ推奨を報告（マージ・pushは人間の承認後）
   - **不合格**: 指摘一覧を本ドキュメントのIssue欄に追記し、エスカレーションルールを適用

### エスカレーションルール（品質不足時）
```
Sonnet で品質不足 → Opus に再割当（指摘一覧を引き継ぎ）
Opus で品質不足   → Fable が自ら実装
同一Issueの差し戻しは2回まで。3回目はFableが引き取る
```
- 「品質不足」の定義: 受入基準の未達、テスト・照合の省略、仕様（事前登録ルール）からの逸脱、
  スコアリングロジック等の変更禁止事項への抵触
- 差し戻し時は担当欄を書き換えて履歴を残す（例: `担当: Sonnet → Opus (2026-07-20 差し戻し)`）

### GitHub Issues / PR について
- 現在 `gh` CLI が未認証のため、Issue管理は当面このドキュメントで行う
- 人間が `gh auth login` を実行すれば、本ドキュメントの各IssueをGitHub Issues化し、
  ブランチ→PR→Fableレビュー（`gh pr view/diff`）のフローに移行できる（リポジトリはpublicである点に注意）
