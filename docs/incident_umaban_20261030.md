# インシデント: 出馬表の枠番を馬番として取得していた（2026-10-30 発覚）

発見: Codex レビュー（京都10R 20261025 の horse_id 照合）→ Claude が全期間照合・DOM確認・修正。

## 何が起きていたか

`race_pickup.scrape_shutuba()` は馬番セルを `td.Num` で探し、無ければ「行内の最初の数字セル」を使っていた。
netkeiba の出馬表に `td.Num` は存在せず、行の先頭は `td.Waku*`（**枠番**）、次が `td.Umaban*`（馬番）。
さらに「同じキーは初回のみ登録」のため、1枠1頭（最大8件）しか残らなかった。

- 影響したマップ: `horse_id_map` / `odds_map` / `pop_map`（同一ループ）
- 影響しなかったもの: `horse_map`（馬名。AI展開図 HorseIcon 由来で正しい）、3指数（speed.html 由来）、
  race_results.json（列位置で取得。馬番重複・馬ID重複・枠順矛盾 0件）
- 期間: 2026-03-28（4532816 初回実装）〜 2026-10-30。horse_id_map を保存している全日付

例（京都10R 15頭）: 保存キー 3→実際は馬番4の馬、4→6、5→8 … 8→14。9〜15番はキー自体なし。

## 馬券成績の比較

**2026-11-07: この比較は撤回した（タスク11。ユーザー決定）。修正の効果の判断には使わない。** 修正前の点数（前走データが別の馬・古い値）で🔥を選んでおり、払戻も JRA 公式と照合していない。作り直した点数での成績は、タスク8・10で出す（まだ終わっていない）。

バグのせいで、保存された馬IDが他の馬を指していることがあった（その馬の前走成績で点数が付く）。

- 本人と一致したのは、たまたま馬番と枠番が同じ馬（主に1・2番、少頭数レース）だけ。その条件自体の影響と区別できない。

- 頭数が少なく偶然の差かもしれない。
- 複勝は、払戻データの欠け（0円扱いになっていた）と不的中を区別していないため、再集計まで判断しない。

- 照合件数の内訳: 採点対象の馬で照合できなかったもの16件、結果データが無いレース21件は比較から外した。

## なぜ気づけなかったか

1. **「値があるか」だけを見て「正しい馬の値か」を見ていなかった。** Phase A 合格判定「オッズ取得率100%」は件数のみ。
2. **異常の兆候を未検証の推測で説明して閉じた。** 2026-07-18 に today_pop 充足率61〜70%横ばいを観測し
   「前日17時はNinki列未表示と推定」で終了（実際は9番以降のキーが無い）。10-28 監査でも充足率66%を欠損問題としてのみ扱った。
3. **画面が正しく見えた。** 馬名は別経路で正しいため表示上の違和感がなかった。
4. **壊れても止まらない設計。** フォールバック・初回のみ登録・例外の握りつぶしで、異常が数値の下振れにしか現れなかった。
5. **テストが無く、正解データ（race_results.json の馬番・馬ID・枠番）と一度も突き合わせていなかった。**

# 追記: 指数の隠し値を指数として読んでいた（2026-10-30 夜に発覚・2件目）

## 何が起きていたか
タイム指数ランキングが未公開のとき（前日の早い時間・6か月以上前の過去レース等）は、代わりに
`speed.html?rf=shutuba_submenu` の各馬の指数セルを読んでいる。このセルには並び替え用の隠し値
（`span.Sort_Function_Data_Hidden`）があり、中身は「1000＋指数」（指数83 → 1083、データ無し → 1000）。
`scraper.parse_speed_shutuba()` はこの隠し値を指数として読んでいた。

- データが無い馬が「指数1000」として上位に入り、3指数すべて1位の馬として採点されていた。
- 実際の指数がある馬は「1000＋指数」として記録された（並び順は保たれるが、データ無しの馬が混ざる）。
- 発見のきっかけ: 2026-10-31 京都4R（障害2910m。タイム指数が無いレース）のグロリアラウスが3指数とも1000.0で8点、
  ペーパートレードの買い目にも入っていた。

## 影響
- 3指数すべて上位3位以内の馬 2,244行のうち **315行（67日分）** に1000以上の値（データ無し103行、1000＋指数212行）。
- 2026-10-31: 京都4Rの採点（8点）とペーパートレードの買い目は無効。買い目ファイルは書き換えず、
  `output/20261031/invalidated.json` に無効の記録を残した。

## 修正
- `scraper.speed_cell_score()`: 隠し値は使わず、画面に見えている文字を読む。`-`・`未`・空はデータ無し。
- 指数が0〜200の範囲外なら、そのモードは使わない（`index_out_of_range()`）。→ **この範囲は誤りだった（下の「追記2」）**
- 回帰テスト `tests/test_speed_index.py`。セル構造は実ページ（race_id 202608041004）で確認。

## 同じ種類の間違いを洗い出すために
取っている値をすべて `docs/data_sources.md` に一覧化し、確認済みか未確認かを明記した。
前走の着順・人気・距離は自前の結果データと照合して確認済み（1,700頭）。
結果データの複勝オッズは JRA 公式と合わないため使えないことも判明した（複勝は payouts_jra.json を使う）。
未確認の項目（前走のタイム指数、各データ上位3頭、データ分析ピックアップ、出走馬分析）は要確認リストに載せた。

# 追記2: 範囲検査の誤りと、近走平均「*」付きの値が候補選びから外れている問題（2026-10-30 深夜）

## 範囲検査の誤り（修正: ブランチ fix/index-range）
- 夕方の修正で入れた「0より大きく200より小さい」は、実データで確かめずに決めた範囲だった。
  - 保存済みランキング98,404件の値は最小-720・最大127。0以下は148件（71日分）あった。
- その結果、2つの誤りがあった。
  - ランキングページ経由: 0以下の値が1つでもあると、その指数1種類を丸ごと捨てる。保存済みの表に当てはめると、10,015表のうち62表が正当な値なのに捨てられる。この判定は 10/30 夕方から入っていたが、本番で動いた取得（10/31分）では該当が無かった。
  - 代わりの取り方: 「72*」やマイナスの値を、数字として読めずデータ無しにしていた。範囲外の値も空文字にしていたので、後の検査で気づけなかった。
- 修正: 値を「正常」「正当なデータ無し」「取得異常」の3つに分ける（`classify_index_text`）。
  - 200以上と未知の形は取得異常とし、そのモードを使わずにログに記録する。
  - 0・マイナス・「*」付きは正常として扱う。
  - 新しい判定を保存済みの全10,015表に当てはめると、捨てるのは732表で、すべて旧コードの隠し値（値がすべて200以上）だった。
    - 2026-11-04 注記（タスク9）: 確かめたのは「読めた整数値がすべて200以上」まで。365表には「-」も入っている。値が隠し値（1000＋指数）であることは実ページで確かめておらず、仮説として扱う。
- テスト: 実ページ4つ（ランキング2、代わりの取り方2）を `tests/fixtures/` に保存して使う。代わりの取り方で作った順位表が、ランキングページと一致することも確かめた。
