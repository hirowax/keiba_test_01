# インシデント: 出馬表の枠番を馬番として取得していた（2026-10-30 発覚）

発見: Codex レビュー（京都10R 20261025 の horse_id 照合）→ Claude が全期間照合・DOM確認・修正。

## 何が起きていたか

`race_pickup.scrape_shutuba()` は馬番セルを `td.Num` で探し、無ければ「行内の最初の数字セル」を使っていた。
netkeiba の出馬表に `td.Num` は存在せず、行の先頭は `td.Waku*`（**枠番**）、次が `td.Umaban*`（馬番）。
さらに「同じキーは初回のみ登録」のため、1枠1頭（最大8件）しか残らなかった。

- 影響したマップ: `horse_id_map` / `odds_map` / `pop_map`（同一ループ）
- 影響しなかったもの: `horse_map`（馬名。AI展開図 HorseIcon 由来で正しい）、3指数（speed.html 由来）、
  race_results.json（列位置で取得。馬番重複・馬ID重複・枠順矛盾 0件）
- 期間: 2026-03-28（4532816 初回実装）〜 2026-10-30。horse_id_map を保存している全日付

例（京都10R 15頭）: 保存キー 3→実際は馬番4の馬、4→6、5→8 … 8→14。9〜15番はキー自体なし。

## 影響件数（125日・1,636レース、読み取り専用照合）

| 項目 | 件数 |
|---|---|
| horse_id_map キー | 正 3,693 / **別馬 5,749** / 照合不能 66 |
| 誤対応を含むレース | 1,095（うち 1,039 はキー＝枠番と完全一致） |
| 3指数重複馬の前走系データ | 本人 494 / **別馬 519** / キー欠損 511 / map空 611 |
| 3指数重複馬の today_odds | 確定オッズと±35%以内は 359件中 126件のみ |

- 別馬データで加点されうる項目: 前走指数HIGH/MID・前走レース内1位・中4週・前走好走・同距離・逃げ。
  「本人」区分でもレース内1位判定の比較母集団（race_max_prev_idx）は壊れている。
- 2026-01-10〜04-18 の大半は horse_id_map が空（別問題・前走系加点なし）。
- index.html の人気バッジ（today_pop）も別馬の人気を表示していた日がある（speed.html フォールバック時は正しい）。
- paper_bets（20260912〜）の買い目馬番自体は正しいが、軸選定のスコアが汚染入力。

## 馬券成績の比較

バグのせいで、一部の馬は**他の馬の前走成績**で点数が付いていた。
「自分のデータで点数が付いた馬」と「他の馬のデータで点数が付いた馬」を、単勝100円ずつ買った場合で比べた（全期間・結果あり）。

**🔥マーク（9点以上）の馬**

| | 買った頭数 | 1着になった割合 | 100円が平均いくらで返ったか |
|---|---|---|---|
| 自分のデータで点数が付いた馬 | 82頭 | 3頭に1頭（31%） | 98円 |
| 他の馬のデータで点数が付いた馬 | 31頭 | 4〜5頭に1頭（23%） | 62円 |

**ペーパートレードと同じ条件（そのレースで1番点が高く、8点以上の馬）**

| | 買った頭数 | 100円が平均いくらで返ったか |
|---|---|---|
| 自分のデータで点数が付いた馬 | 111頭 | 109円 |
| 他の馬のデータで点数が付いた馬 | 52頭 | 78円 |

結論: 正しいデータで点数が付いた馬の方が成績は良く見えるが、**「修正すれば儲かる」とはまだ言えない**。
- 正しく点数が付いたのは、たまたま馬番と枠番が同じだった馬（主に1番・2番、頭数の少ないレース）だけ。その条件自体が成績に効いている可能性を消せない。
- 頭数が少なく、偶然の差かもしれない。修正後のデータを1〜2か月ためて確認する。
- 前走成績のデータ自体が無かった馬（2026-01〜04の大半など）は比較から外した。この時期は結果データの複勝払戻も約半数欠けている。

## なぜ気づけなかったか

1. **「値があるか」だけを見て「正しい馬の値か」を見ていなかった。** Phase A 合格判定「オッズ取得率100%」は件数のみ。
2. **異常の兆候を未検証の推測で説明して閉じた。** 2026-07-18 に today_pop 充足率61〜70%横ばいを観測し
   「前日17時はNinki列未表示と推定」で終了（実際は9番以降のキーが無い）。10-28 監査でも充足率66%を欠損問題としてのみ扱った。
3. **画面が正しく見えた。** 馬名は別経路で正しいため表示上の違和感がなかった。
4. **壊れても止まらない設計。** フォールバック・初回のみ登録・例外の握りつぶしで、異常が数値の下振れにしか現れなかった。
5. **テストが無く、正解データ（race_results.json の馬番・馬ID・枠番）と一度も突き合わせていなかった。**

## 修正（ブランチ fix/umaban-mapping）

- `race_pickup.parse_shutuba_rows()` を新設。馬番は `td.Umaban*` のみ。最初の数字へのフォールバック廃止。
- 同一行から馬番・馬名・馬ID・単勝オッズ・人気を取る。`map_issues` で以下を検出:
  `row_without_umaban` / `dup_umaban` / `dup_horse_id` / `missing_horse_id` / `umaban_not_contiguous` /
  `missing_vs_horseicon`（AI展開図の馬番集合との不一致）/ `no_rows`
- `map_issues` があるレースは run_pickup_all / rerun_failed_pickup でスコアリングせず `error` として記録（公開しない）。
- `odds_status`（ok / unsold / scratched / no_cell / unparsable）で未発売・取消を馬ID欠損と区別して保存。
- pickup_scores.json に `collector_version: 修正後_20261030_馬番を正しく取得` を記録（ファイル単位・レース単位）。この項目が無いデータ＝修正前。
- 回帰テスト `tests/test_shutuba_mapping.py`（5〜18頭・取消・未発売・ID欠損・馬番セル欠損・部分欠損・重複）。
- 実ページ（京都10R 20261025, 15頭）で 馬ID 15/15・オッズ 15/15 が結果データと一致することを確認。

## 過去データの扱い

- 過去の pickup_scores.json / paper_bets.json / threshold_config.json は**上書きしない**。
- 研究・検証では `collector_version` が無い（＝修正前）データの前走成績による加点・today_odds・today_pop・odds_map・pop_map を
  **信頼しない**。horse_id は race_results.json から正しく復元できるが、当時のオッズ・人気は復元できない。
- 旧閾値（ev_threshold=9）・v5 の実績値・v6 の検証・sol 監査（32日328頭 等）はすべて修正前のデータに基づく。再評価が必要。
- 修正後はスコア式が同じ v5 でも入力が変わるため、旧閾値の意味は変わる。

## 再発防止（恒久ルール → CLAUDE.md「データ整合性ルール」）

- スクレイプは要素をクラス名等で明示して取る。「最初の数字」等の位置推測フォールバックを書かない。見つからなければ失敗させる。
- 「初回のみ登録」で重複を黙って捨てない。重複は異常として検出する。
- 取得率と正しさを分けて報告する。新しい取得項目は正解データ（race_results.json）との照合を合格条件にする。
- 異常値を推測で説明したら、その推測を検証するまで閉じない。
- パーサー変更時は `python3 -m unittest discover -s tests` を通す。
