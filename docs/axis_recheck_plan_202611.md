## 4. 進め方（案A: 前向きの記録）
### 4.1 候補の決め方（案。記録を始める前に固定する）
候補は少なくする（多いほど、選ぶ期間で偶然よく見えるものを選びやすい）。案は次の4つ。
| 候補 | 決め方 | 軸を出さないレース |
|---|---|---|
| 候補1 | v5.2 の点数1位（下限なし） | 候補がいない・点数が付かない |
| 候補2 | v5.2 の点数1位で、点数が N 点以上（N は記録を始める前に1つ決める） | 候補1に加えて、N 点未満 |
| 候補3 | 3指数の候補のうち、3指数の順位（ページの順位）の合計が最も小さい馬（点数を使わない） | 候補がいない |
| 比べる基準 | 単勝1番人気（採点した時点の人気。そのレースの出走全馬から選ぶ） | 確認不能（下） |

- **比べる基準（単勝1番人気）は、比べるためだけに使い、採用の候補にしない。** 採用の候補は、候補1〜3の3つ。
- 候補2の N は 8 とする（案）。修正前のデータで決めた今の買い目の下限と同じ値だが、それが有効だった根拠として使うのではない。記録を始める前に決めた、比べる候補の1つとして使う。
- 比べる基準の選び方（2026-11-10 追記）:
  - 3指数の候補（`scored`）の中の最も人気の馬ではなく、そのレースの出走全馬（出馬表で取消・除外の馬を除く）から、採点した時点（前日 17:00 の採点）の人気が1の馬を選ぶ。人気は `pickup_scores.json` の `pop_map`（馬番ごとの人気）を使う。
  - 出走する馬のうち1頭でも人気が取れていない、または `pop_map` が無いときは、比べる基準だけを「確認不能」とする（候補1〜3には影響しない。件数を出す）。
  - 人気が1の馬が2頭以上いるときは、比べる基準だけを「同点で決められない」とする。
  - 前日 17:00 の人気は前売りのもので、発走時の人気とは違う。候補1〜3と同じ時点で使える情報で比べるため、この時点の人気を使う。

- 同点の扱い（最上位の同点だけ。例を付けて固定する。2026-11-10 改訂）:
  - 候補1・2: **最高点の馬が2頭以上いるときだけ**、そのレースは「同点で決められない」として軸を出さない（件数を出す）。下位の同点は関係しない。今のコードの「一覧で前にある馬」は使わない。
    - 例: 10点・10点・9点 → 軸なし（同点）。10点・8点・8点 → 10点の馬。10点・9点 → 10点の馬。
    - 候補2は、最高点の馬が1頭で、その点数が N 点以上のときだけ軸を出す。例（N=8）: 9点・9点 → 軸なし（同点）。7点・6点 → 軸なし（N 点未満）。
  - 候補3: **順位の合計の最小値の馬が2頭以上いるときだけ**、軸を出さない（件数を出す）。例: 合計 4・4・6 → 軸なし。合計 3・5・5 → 合計3の馬。
- 欠損: 品質の判定（`data_quality.race_quality_issues()`）で問題があるレースは、どの候補でも軸を出さない（理由ごとに件数を出す）。
  - この記録は、v5.2 で買い目を止めていること（`paper_trade.py` の「点数の版 v5.2 には買い目の基準が無い」）とは独立した研究用の記録で、買い目の有無には関係なく記録する。（2026-11-10: 「この理由だけは問題にしない」という例外を削除した。この理由は `race_quality_issues()` の結果には入らず、例外が働く場面が無かったため。）

### 4.2 記録
- `run.sh` の採点の後に、候補ごとの軸を記録するスクリプトを足す（`output/{date}/axis_candidates.json`）。記録は、結果が出る前（前日 17 時の採点の後）に書き、後から書き換えない。
- 記録する値: レースID、候補ごとの軸の馬番・馬名・馬ID（または軸を出さない理由）、点数・順位・人気、品質の判定の結果、記録した時刻、この計画の版（改訂の記録の日付）、使ったコードのコミット。
- 版: `SCORING_VERSION`・`DATA_TOP_READER_VERSION`・`COLLECTOR_VERSION`・`PREV_FETCH_VERSION`・`TOP1_RULE`・`INDEX_READER_VERSION`・`CANDIDATE_RULE_VERSION`・`INDEX_TABLE_CHECK_VERSION`。品質の判定（`data_quality.py`）には版の値が無いので、ファイルの sha256 を記録する。
- 入力ファイルのハッシュ: そのレースの採点に使った `pickup_scores.json`・`全場_3指数重複馬.csv`・`prev_inputs/{実行ID}.json` の sha256。
- 記録の状態を、レースごとに次の3つで区別する（2026-11-10 追記）:
  - 軸あり: 正常に判定して、軸を決めた。
  - 軸なし: 正常に判定した結果、軸を出さない（理由: 候補がいない・同点・N 点未満・品質の問題・確認不能 など）。
  - 記録なし: 記録のスクリプトが失敗した、または実行されず、そのレースの記録が無い。
  - **記録なしを、軸なし（購入0件）として扱わない。** 評価では別に件数と日を出す。
- 記録のスクリプトが失敗しても、採点・公開・買い目の処理は止めない（`run.sh` の `paper_trade.py` と同じ扱い）。失敗は、ログに残し、LINE で通知する（通知の方法は設計で決める）。
- 取り直しの規則:
  - 期限は、対象日の 00:00（日本時間）。前走データの取得の期限と同じ。期限を過ぎたら取り直さない。
  - 入力は、保存してある入力（`pickup_scores.json`・`全場_3指数重複馬.csv`・`prev_inputs/{実行ID}.json`）だけを使う。ページを取り直さない。
  - 記録は、レースごとに追加するだけで、すでにあるレースの記録は書き換えない。
  - すでに記録があるレースは、そのレースの入力（`pickup_scores.json` のそのレースの部分と、使った前走データ・指数の候補の行）が記録と同じなら何もしない。違うなら、そのレースは止めて（記録を書き換えず）、理由をログに出す。ファイル全体の sha256 も記録するが、ほかのレースの採点し直しでファイル全体が変わることがあるので、同じかどうかの判定はレースの部分で行う。
  - まだ記録の無いレース（前の実行の失敗、採点エラーで後から `rerun_failed_pickup.py` で採点されたレース など）は、期限内なら、その時点の保存入力から記録してよい。記録した時刻を残す。
- 実装・テストは、この計画の承認後に別に行う（実装の前に、変更内容を説明して同意を得る）。

### 4.3 期間（選ぶ期間と、確かめる期間を分ける）
- 選ぶ期間: v5.2 の本番が始まった開催日から、**X 開催日**。この期間の結果で、候補1〜3から1つを選ぶ（選び方は下）。
- 確かめる期間: 選ぶ期間が終わった次の開催日から、**Y 開催日**。選んだ1つだけを確かめる。採用の根拠は、確かめる期間の結果だけにする。
- 案: X = 16、Y = 16（中央の開催は1週あたりおよそ2日なので、それぞれ約2か月）。
- 終了の条件は、件数ではなく開催日数で決める（途中の成績で終わりを動かさない）。
- 途中で見るのは、取得・記録の異常（記録が無い日、品質の問題の件数）だけ。成績は期間が終わるまで集計しない。
- 記録なし（4.2）の日・レースも、予定の開催日数に数える。記録なしがあっても、期間を延ばさない。
- **選ぶ期間の欠損（2026-11-10 追記）:**
  - 選ぶ前に、選ぶ期間の候補1〜3の購入について、結果（着順・取消・除外・中止・失格）・返還・複勝の払戻をすべて確定させる。
  - 記録なし（4.2）が1レースでも残っている、または確定できない購入が残っているあいだは、選ばない（保留）。期限内の取り直しで記録が埋まった場合と、払戻などを後から取れた場合は、埋まった後の値で選んでよい。期間は延ばさない。
    - 記録なしは、取り直しの期限（対象日の 00:00）を過ぎると埋められない。期限を過ぎた記録なしが残ったときは、この期間では選ばずに終え、記録なしの日・レースと理由を報告する。
  - 払戻の取得と確かめ（担当と時期）:
    - 払戻は cron では取っていないので、`scrape_jra_payouts.py`（手動）で取る。
    - 各開催週の翌週の水曜日までに、その週の開催日の払戻を取る。あわせて、記録のある購入のうち、結果・払戻が欠けているものを一覧にする（一覧を出す処理は、評価のスクリプトに入れる。成績は出さない）。
    - 選ぶ期間が終わった後に、もう一度欠けを一覧にし、欠けが無いことを確かめてから選ぶ。
- **確かめる期間の始まり（2026-11-10 追記）:**
  - 選んだ候補を固定した時刻（選んだ結果を書いた時刻）を記録する。
  - 確かめる期間は、固定した時刻より後の、最初の開催日から始める。予定では「選ぶ期間が終わった次の開催日」だが、それまでに選べなかったときは、選べた後の最初の開催日から始める（成績を見ずに決まる規則にするため）。
  - 選ぶ期間が終わってから確かめる期間が始まるまでの開催日は、記録は続けるが、どちらの期間にも入れない（件数だけ出す）。
- **選び方（選ぶ期間の結果だけで決める。案）:**
  1. 購入が 50件以上、かつ購入のある開催日が 8日以上の候補だけを選べる。どの候補も届かなければ、選ばずに終える（確かめる期間に進まない）。
  2. 選べる候補のうち、複勝回収率（4.4 の計算。区間ではなく点の値）が最も高いものを選ぶ。
  3. 複勝回収率が同じ（小数第1位まで同じ）なら、候補2 → 候補1 → 候補3 の順で先のものを選ぶ（候補2 は今の買い目の決め方に近いため）。
  - 例: 候補1 が 92.3%（120件・15日）、候補2 が 95.0%（48件・9日）、候補3 が 88.1%（160件・16日） → 候補2 は件数が足りないので選べず、候補1 を選ぶ。
- **コードが変わったとき（先に決めておく。2026-11-10 改訂）:**
  - 記録のための識別: 4.2 の版・コミット・各ファイルの sha256 は、変更の大小によらず毎回記録する。
  - 評価の扱いは、変更の中身で分ける:
    - 点数・候補・軸・対象レースの選び分け（品質の判定を含む）に影響する変更: 選ぶ期間または確かめる期間の途中で入れたら、その期間はその日の前で終える。変わる前と後の記録は混ぜない。
    - コメント・ログ・表示だけの変更: 評価を続ける。
    - どちらか判断できない変更: 影響する変更として扱う。
  - 分類は、変更を入れる前に、成績を見ずに決め、根拠とともにこの計画書の末尾の「コードの変更の分類の記録」に書く。入れた後に分類を変えない。
  - 影響する変更で期間を終えたとき: 記録は続ける。正式に評価する期間は、その変更を入れた後の最初の開催日から、同じ規則で選ぶ期間からやり直す（やり直したことと日付を改訂の記録に書く）。終えた期間は、途中までの件数だけを報告し、成績では選ばない。
  - 既知の不具合（障害戦の前走、前走の着順「取消」の表記、脚質の作り直し など）は、評価を完成させるために直さずに残すことはしない。直すと、上の規則で期間がやり直しになる。

### 4.4 評価
- 照合: 軸の馬を選んでから、結果（`race_results.json`・`race_nonfinishers.json`）と、馬番と馬名の両方で照合する（馬名の違いで許すのは空白だけ）。照合できない馬は種類別に件数を出す。
- 分母と払戻:
  - 取消・除外: 的中率の分母から外す。馬券は返還なので、購入額にも払戻額にも入れず、返還の件数・金額を別に出す。
  - 競走中止・失格: 分母に入れ、不的中とする。
  - 状態が分からない: 推定せず、未確認として件数を出す。
  - 払戻は JRA 公式（`payouts_jra.json`）だけを使う。払戻が取れていないレースは、0円にも返還にもせず、回収率の集計から外して件数を出す。
- 出す数字（候補ごと、期間ごと）:
  - 対象レース数（採点したレース）、軸を出したレース数、出さなかったレース数（理由別）
  - 購入額、払戻額、返還額
  - 回収率 = 払戻総額 ÷ 購入総額（返還分を除く）。単勝・複勝それぞれ
  - 1着率、3着内率
- **主な指標は複勝回収率に固定する。** 単勝回収率・1着率・3着内率は参考として出すだけで、採用の判断に使わない（複勝で届かなかったときに単勝で採用することはしない）。
- 不確かさ: **開催日を単位に、日を復元抽出するブートストラップ**で区間を出す。同じ開催日のレースは、馬場などを共有していて独立とは限らないため。計算の条件（案）:
  - 対象の日: 期間のすべての開催日。購入が0件の日も残す（抽出されれば、購入0円・払戻0円の日として入る）。
  - 1回の抽出: 期間の開催日数と同じ数の日を復元抽出し、選ばれた日の「払戻の合計 ÷ 購入額の合計」を計算する（レースごとの回収率の平均ではない）。返還分は購入額にも払戻にも入れない。
  - 抽出で購入額の合計が0円になった回は、回収率を計算できない回として数える。その回は区間の計算から外さず、回収率0%として扱う（よく見える方向に外さないため）。その回数も報告する。これはこの計画で決めた便宜上の扱いで、ふつうの回収率（払戻総額 ÷ 購入総額）とは別のものとして書く。
  - 抽出の回数: 10,000回。乱数の種: 20261109。計算に使う日の並びは日付の順。
  - 区間: 片側95%の下限（10,000回の値を小さい順に並べた5%点。パーセンタイル法）。
  - 候補どうしの比べ（参考）: 同じ抽出（同じ日の組）で両方を計算し、差の両側95%区間を出す。選ぶ期間の選択には使わない（選び方は 4.3）。
  - 限界: 日をまたいだ関連（同じ馬が何度も出走する、など）は扱えない。開催日数が少ないと、パーセンタイル法の区間は狭く出やすく、95%と書いた区間が実際には95%より低い割合でしか真の値を含まないことがある（2026-11-10 の外部レビューで、小標本のブートストラップの注意点の参考として https://arxiv.org/abs/1411.5279 が示された）。基準が厳しいから誤って採用することが起きにくい、とは言えない。
- **判断に必要な件数（案）:** 確かめる期間で、選んだ候補の購入が 100件以上、かつ購入のある開催日が 12日以上。届かなければ、採用も不採用も決めず「判断保留」とする（期間は延ばさない）。最低件数は分析を始める目安で、十分な証拠の保証ではない（16開催日・100件で、採用できる精度が得られる保証はない）。
- **欠損があるとき:** 確かめる期間の選んだ候補で、返還かどうか・結果・複勝払戻のどれかを確定できない購入が1件でも残れば、「判断保留」とする。記録なし（4.2）が1レースでも残れば、同じく「判断保留」とする。欠損を後から埋めた場合は、埋めた後の値で判断してよい。ただし、評価する期間は延ばさない。払戻の取得と確かめの時期は、選ぶ期間（4.3）と同じ。
- 採用の基準（案）: 確かめる期間で、選んだ候補の複勝回収率の片側95%の下限が Z = 100% 以上なら、買い目の軸として**採用を提案する**（提案にとどめ、採用はユーザーが決める）。届かなければ採用しない（基準を下げない）。
  - 届かなかったときは、「利益が無いと示された」とは書かず、「採用の条件を満たす証拠が得られなかった」と書く。
