## 2. cookie の有効性判定（重要な教訓）

### 期限日では判定できない

2026-10-02 の実測で、`nkauth` 残 352 日・`netkeiba` 残 351 日と**期限上は有効なのに
サーバー側セッションが無効化されていてログアウト状態**だった。cookies.json の
`expires` を見るだけでは切れているかどうか分からない。

### 正しい判定手順

1. レース一覧から **10R〜12R** の race_id を取る（1R は使わない）
2. `preflight_premium_check()`（`scraper.py:245`）を 1〜2 本実行
3. 併せて `https://regist.netkeiba.com/account/?pid=login` に「ログアウト」リンクが
   あるか（= ログイン中）を確認

**1R を使わない理由**: 1R は新馬戦のことが多く、新馬は**タイム指数そのものが存在しない**ため
FAIL が出ても cookie 切れとは断定できない。実際 2026-10-02 に東京1R で FAIL → 後半レースで
再確認して本物の期限切れと確定した、という切り分けを行っている。

> `scraper.py:815` の本番プリフライトは `races[0]` 固定なので、この誤判定を起こしうる（未修正）。

### 実測した有効期間

| 再ログイン日 | 次に切れを確認した日 | 持続 |
|---|---|---|
| 2026-09-19 04:45 | 2026-10-02（FAIL） | 13 日 |
| 2026-10-02 15:43 | 2026-10-10（FAIL） | 8 日 |
| 2026-10-10 22:38 | 2026-10-23 時点で有効 | 13 日以上 |

CLAUDE.md の「数週間に1回程度」より短い。**開催前日の実行前に毎回実測する**のが安全。

切れていた場合の対処は手動ログインのみ:

```bash
python3 save_cookies.py
```

## 3. 手動実行の手順（cron 未実行時）

netkeiba への同時アクセスを避けるため**逐次**実行する。`run.sh` は同時実行不可。

```bash
# ① cookie 実測（上記 2 の手順）
# ② 翌日のデータ取得
AUTO_MODE=1 bash run.sh YYYYMMDD
# ③ 3分休憩（IPブロック対策）
# ④ 当日の結果取得
python3 scrape_results.py YYYYMMDD
git add output/YYYYMMDD/ && git commit -m "results: YYYYMMDD" && git push
```

### 注意: 18:30 の結果 cron と衝突する

2026-10-17 に、18:30 の結果 cron（`run_results_cron.sh`）と手動の `run.sh` が
**18:30〜18:48 の間同時に netkeiba へアクセスした**。両方成功したが避けるべき状態。

開催当日の夕方に手動実行する場合は、結果取得をチェーンから外して cron に任せるか、
18:30 を避けて起動する。

また `run.sh` は**プリフライト失敗でも後続処理に進む**（2026-10-10 に確認）。
cookie 切れのまま起動すると空データでピックアップ・push が走りうるので、
①の実測を省略しないこと。
