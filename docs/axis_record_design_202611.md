# 買い目の軸の再検証の記録の設計（2026-11-12）

計画は `docs/axis_recheck_plan_202611.md`（2026-11-12 承認）。この文書は、計画を `axis_record.py` でどう実装したかと、計画に書いていない細かい決め方をまとめる。2026-11-12 の外部レビュー（設計へのレビュー）を反映した。

## 1. 動く場所
| 処理 | いつ | 何をする |
|---|---|---|
| `axis_record.py record {日付}` | `run.sh` の `paper_trade.py generate` の後、git add の前（前日 17:00 の自動実行） | 予定のレースを保存し、レースごとに候補1〜3・比べる基準の軸を決めて `output/{日付}/axis_candidates.json` に足す。記録は 17:00 の後の commit で GitHub に push される |
| `axis_record.py check` | `run_cron.sh` の最初（毎日 17:00。Mac が起きていれば開催日でなくても動く） | 開始日からの開催日の、記録の欠けと、結果・返還・複勝の払戻の欠けを調べる。成績は出さない |
| `axis_record.py restore {日付} --reason ...` | 手動 | 期限前に GitHub の main にあった commit の入力とコードだけで計算し直し、記録の無いレースを足す |
| `axis_record.py compute {日付} --out ...` | `restore` の中だけ | ファイルを読んで計算するだけ（何も書き換えない） |

## 2. 記録（計画 4.1・4.2）
### 2.1 予定のレース
- 予定のレースは `全場_3指数重複馬.csv` に載ったレース。見出しの行・列の数・開催場・レース番号・馬番・重複を検査する。
- CSV が無い・壊れている → 「予定のレースを確定できない」（対象0件にしない）。見出しだけで候補0件 → 「確定」で0レース。
- 予定は、軸の計算より先に記録ファイルに保存する。確定した予定と後の CSV が違えば、元の予定を残して止める。

### 2.2 軸の決め方（`decide_race`）
- 候補1・2: 採点の候補（`scored`）の最高点の馬が1頭なら軸。最高点が2頭以上なら「同点で決められない」。候補2は、さらに 8点以上のときだけ軸。
- 候補3: CSV の候補（出馬表で取消・除外の馬を除く）の、3指数のページの順位（「1位」などの表記）の合計が最小の馬。1頭でも順位が読めなければ、候補3全体を「確認不能」にする（読めた馬だけで選ばない）。最小が2頭以上なら「同点で決められない」。
- 比べる基準: 出馬表の全部の馬（`horse_name_full`。出馬表の行から作り、馬番が 1〜N までそろうことを採点のときに確かめている）から、取消・除外（`scratched_nums`）を除いた出走馬のうち、`pop_map` の人気が1の馬。人気が欠けた出走馬が1頭でもいれば「確認不能」（`pop_map` にある馬だけで選ばない）。人気1が2頭以上なら「同点で決められない」。
- 品質の判定（`data_quality.race_quality_issues()`。その時点の `invalidated.json` を含む）が正常にでき、問題があるレースは、比べる基準も含め、すべて「軸なし（品質の問題）」。比べる条件をそろえるため。
- 「記録できない」（軸なしにしない）: 採点結果にレースが無い、ファイルを読めない、出馬表の馬の一覧・採点の候補・点数が無い・読めない、CSV の候補（取消を除く）と採点の候補が違う、など。
- 確かめたこと（2026-11-12）: 10/31・11/1・11/7・11/8 の保存データで、CSV のレースはすべて採点結果にあり、CSV の候補（取消を除く）と採点の候補は全レースで一致した。人気が欠けた出走馬はいなかった。この4日はすべて品質の問題（出走馬分析の読み方が修正前）で軸なしになる。品質の判定だけを外した試しでは、どのレースも例外なく判定できた（判定の内訳だけを見た。成績は見ていない）。

### 2.3 採点エラーのレース（計画に無い細かい決め方）
- 採点エラー（`pickup_scores.json` のレースに `error`）は、記録にせず「採点エラーで保留」（`pending`）に置く。期限内に `rerun_failed_pickup.py` で採点し直されれば、記録を足せる（計画 4.2 の「まだ記録の無いレース」）。
- 期限を過ぎても保留のままなら、品質の問題（採点エラー）による軸なしとして扱う。「記録なし」（スクリプトの失敗）とは区別する。

### 2.4 同じ入力かどうか・書き換えない
- レースごとに `input_key`（sha256）を持つ。中身は: 計画の版（`AXIS_PLAN_VERSION`）、N、`axis_record.py` と `data_quality.py` の sha256、`pickup_scores.json` のレースの外の情報（日付・点数の版・馬番の版など）、そのレースの採点結果の全体、CSV のそのレースの行、その時点の無効の理由。
- すでに記録があるレースは、`input_key` が同じなら何もしない。違えば（今は記録できない場合も含め）書き換えずに止め、問題として返す（終了コード1 → 通知）。
- `axis_record.py` のコメントを直しただけでも `input_key` は変わる。同じ日の再実行で止まる側に倒している。
- 記録する識別（同じかどうかの判定には使わない）: 版8つ、コードの commit と未コミットの変更の有無（追跡している .py の変更と、判定に使う6ファイルが commit されていないこと）、各ファイルの sha256、記録した時刻、計画の commit（`AXIS_PLAN_COMMIT`）。
- 計画の版は、数字・軸の決め方・除外の条件などを変えたら上げる（計画書の改訂の記録にも書く）。

### 2.5 期限・ロック・壊れない書き方
- 期限（対象日の 00:00 日本時間）を過ぎたら `record` は何も書かない（終了コード0。欠けは `check` が知らせる）。`run_cron.sh` が過去の日に `run.sh` を動かす補完の経路でも、同じく何も書かない。
- 同じ日の `record`・`restore` は、`output/{日付}/.axis_record.lock`（OS のファイルロック。gitignore 済み）で同時に動かさない。ロックを取れなければ止める。
- 記録ファイルは一時ファイルに書いてから置き換える。途中で止まっても、元のファイルは壊れない。壊れた記録ファイルは上書きせずに止める。

## 3. 欠けの検査（計画 4.3）
- 開始日（`AXIS_START_DATE`）から今日までの、JRA カレンダーの開催日を調べる（記録ファイルがある日から決めない）。開始日が未設定なら何もしない。
- 記録なし（期限を過ぎた日）: CSV から作った予定のレースのうち、記録も採点エラーの保留も無いレース。記録ファイルが無い・壊れている日、予定を確定できない日、記録の予定が CSV と違う日も含む。見つけたら、すぐ知らせる（復元できる場合があるため）。
- 結果・払戻の欠け（開催日の翌日から）: 軸ありの購入（候補1〜3・比べる基準）ごとに、精算と同じ判定で確定できるかを見る。結果に馬番・馬名がそろって出走していれば、そのレースの複勝の払戻があること。結果に無ければ、払戻の返還（取消・除外）か、`race_nonfinishers.json` の中止・失格（馬名も一致）であること。当たり外れは返さない。
- 払戻の期限: 対象日より後の最初の水曜日の終わり（例: 土 11/14・日 11/15 → 水 11/18 の終わり。月 11/23 → 水 11/25 の終わり）。期限を過ぎた欠けだけを知らせる。
- 状態のファイル `output/axis_check_status.json`（gitignore 済み）: 最後に検査が最後まで終わった時刻（`last_completed_at`）と、欠けがあるか（`has_gaps`）・件数・一覧を分けて書く。検査が失敗したら書き換えない。
- `record` は、状態のファイルの最後の成功が8日より前（または一度も無い）なら `AXIS_CHECK_STALE` を出す（開始日が決まった後だけ）。

## 4. 通知
- 記録の失敗: `run.sh` が `AXIS_RECORD_FAILED` の行を出し、`run_cron.sh` がその回の `run.sh` の後に見つけて LINE で知らせる（印のファイルは使わない）。
- 欠けの検査: `check` の終了コードが2（知らせる欠けがある）なら、`AXIS_NOTIFY` の行（件数・日・レースだけ。成績は載せない）を LINE で知らせる。終了コードが0・2以外（検査そのものの失敗）なら、失敗を知らせる。
- 検査の停止: `record` の `AXIS_CHECK_STALE` を `run_cron.sh` が見つけて知らせる。

## 5. 復元（計画 4.2）
- 期限前に GitHub にあったことは、GitHub 側の push の記録（`gh api repos/hirowax/keiba_test_01/activity`。時刻はサーバーが付ける）で確かめる。commit の日時は使わない（古い日時の commit を期限後に push できるため）。
- 期限より前の最後の main への push の、push 後の commit（`after`。完全な ID）を使う。その commit について、次をすべて確かめ、1つでも満たさなければ断る:
  - 手元に commit がある（無ければ `git fetch origin` をしてからやり直す）
  - `output/{日付}/全場_3指数重複馬.csv`・`output/{日付}/pickup_scores.json`・`axis_record.py` がある
  - 承認した計画の commit（`AXIS_PLAN_COMMIT`）を含む
  - その commit を一時的な作業場所（git worktree）に取り出し、その中のコードで `compute` だけを動かす（ネットワークからデータを取らず、採点・買い目・公開を動かさない）。計算に使ったコードの commit が一致し、未コミットの変更が無い
- 足すのは記録の無いレースだけ。記録には、モード「復元」、復元した日時・理由・使った commit・push の時刻を残す。すでにある記録は書き換えない（違えば問題として返す）。
- 限界: GitHub の push の記録は、取れる範囲（2026-11-12 に確かめたところ最大300件。3/28 まで）より古くなると確かめられず、そのときは断る。11/8 で試したところ、期限前の push の commit（f230977）に `axis_record.py` が無いので、正しく断った。成功する復元は、記録のスクリプトが main に入った後の日でないと試せない（試験用の一時リポジトリでは確かめた）。

## 7. 確かめていないこと
- 本番の `run.sh`・`run_cron.sh` からの実行と、LINE への実際の送信。
- 成功する復元を、本物の GitHub の push の記録で試すこと（main に入った後の日でないとできない）。
- 少頭数で複勝が発売されないレース。そのときは「複勝の払戻が無い」の欠けが残り続ける（起きたら扱いを決める）。
- `invalidated.json` を期限の後に足した場合は、記録には入らない（記録は期限前の判定）。評価のときの扱いは、評価のスクリプトで決める。
