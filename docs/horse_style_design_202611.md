    - `schedule_check`（上）。

## 3. 脚質の全体を作る（`build_horse_style.py`）
### 3.1 関数と版
- `STYLE_BUILD_VERSION = "全レース_発走頭数_全馬の最初の通過順が確かめられるレース_前日より前_20261112"` のような、内容の分かる文字にする（実装のときに決める）。
- `select_inputs(target, commit)`: 基準の commit にある `output/{日付}/race_results_all.json` のうち、日付が「対象日の2日前以前」のものを選ぶ。
  - 日曜の対象日なら土曜は入らない。祝日の月曜なら土曜まで入り、日曜は入らない。
  - 一覧は `git ls-tree` で取る。
- `read_blob(commit, path)`: `git show {commit}:{path}` で読む。作業ファイルは読まない。
- `race_verdict(race) -> (使う/使わない, 理由)`: 計画 2.2 の規則。理由の判定の順番（1つのレースは最初に当たった理由1つで数える）:
  1. 着順の状態が知らない表記の馬がいる → 「4 状態不明」
  2. 発走した頭数（着順のある馬＋中止＋失格）が8未満 → 「5 8頭未満」
  3. 着順のある全馬の通過順が空 → 「1 未取得」
  4. 中止・失格の馬の最初の通過順が無い、またはその先頭の値が完走した馬の先頭の値と同じ地点だと確かめられない → 「2 中止・失格の最初の通過順を確かめられない」
  5. 新潟の芝1000m（1つの値が何の地点か確かめていない）、または完走した馬どうしで通過順の値の数が違う（先頭の値が同じ地点か確かめられない）、または通過順のセルが無い → 「3 最初の通過順として使えると確かめられない」
  6. 着順のある馬の一部だけ通過順が空、馬IDが無い・同じ馬IDが2回、最初の通過順が 1〜発走した頭数の外 → 「4 不整合」
- 値の数の違いだけで使えないとはしない。基準は「全発走馬の先頭の値が同じ地点を指すと確かめられるか」。
  - 完走した馬どうしで値の数が同じなら、先頭の値はそのレースで記録された最初のコーナーとみなす。根拠は、実ページで、馬の行の値と、同じページのコーナーごとの通過順位の表が一致するかで確かめる（5章の4。確かめるまでは、この規則を本番に入れない）。
  - 中止の馬の値の数が、完走した馬と違う場合（途中までしか値が無いなど）は、同じページのコーナーごとの通過順位の表に、その馬が最初のコーナーで載っているかで確かめる。確かめる方法が実装されるまでは、このレースを使わない（理由2）。
- `build(target, commit) -> dict`:
  - 使うレースの各馬の相対位置 `(最初の通過順−1)÷(発走した頭数−1)` を馬IDごとに集め、平均で分類する。分類の境目は今の `THRESHOLDS` のまま。
  - 同じ順位の馬は、どちらもその順位で数える。実ページの「13-13」が2頭いる例があるので、同じ位置を異常にしない。
  - 使えたレースが0件なら作成失敗にする。
- `legacy_build()`: 今の作り方（採点したレースだけ・着順のある馬の数で割る）を、ファイルに書かずに dict で返す。比べるためだけに使う。
- 引数なしで動かしたときに `output/horse_style.json` を上書きする今の動きは止める。理由を出して終わる（計画 2.4: `horse_style.json` は書き換えない）。

### 3.2 その日の記録（`output/{対象日}/horse_style/{実行ID}.json`。git に入れる）
```
{
  "status": "作成成功" | "作成失敗",
  "target_date", "run_id", "style_build_version",
  "code": {"commit": 作った時点の HEAD, "build_horse_style_sha256": ...},
  "base_commit": 入力を読んだ commit,
  "started_at", "inputs_fixed_at", "finished_at",       # 日本時間
  "inputs": [{"path", "sha256", "blob"}],                # 使った日・使わなかった日の両方
  "period": {"first", "last"},
  "days_excluded": {日付: 理由},                          # complete でない・開催場のレースがそろわない など
  "races_used": 件数, "races_excluded": {理由: 件数}, "races_excluded_list": [[日付, レース, 理由]],
  "horses": {馬ID: {"style", "avg_ratio", "n_races"}},   # n_races = 分類に使えた出走の数
  "counts": {"horses", "2走以上", "1走", 脚質ごと},
  "failure": {"reason"}                                   # 作成失敗のときだけ
}
```

### 3.3 作る・使う・確定（`ensure_style(target)`。`run_pickup_all.py` の最初で呼ぶ）
- ロックは `output/{対象日}/horse_style/.lock`（`fcntl.flock`。gitignore に足す）で、確かめてから保存し終えるまで持つ。
- 手順:
  1. その日のフォルダの記録（`*.json`）を**すべて読んで検査する**（`check_record`）。1つでも、読めない（壊れた JSON）・形が違う・知らない `status` のものがあれば、無視して新しく作ることはせず、止める（`HORSE_STYLE_RECORD_FAILED` で知らせ、手で調べる）。
  2. 「作成成功」の記録を使う前に、次をすべて確かめる: `target_date` が対象日・`run_id` がファイル名と同じ・`style_build_version` が今のコードの版・`finished_at` が対象日 00:00 より前・`horses` と件数（`counts`）の形が合う・`base_commit`・`inputs` がある。1つでも合わなければ止める（作り直さない）。
     - 版が今のコードと違う成功の記録がある日（実装を入れ替えた日など）も、止める。その日の扱いは手で決める（計画 2.7: 規則の外の作り直しはしない）。
  3. 合格した「作成成功」が1つあれば、それを使う（作らない）。2つ以上あれば止める。
  4. 成功の記録が無く、検査に合格した「作成失敗」の記録だけなら作る（計画 2.6）。今が対象日 00:00 以上なら作らず、「期限の後」の作成失敗を記録する。
- 作る手順:
  1. `HEAD` を基準の commit に固定する。
  2. 入力の各ファイルについて、基準の commit の blob と作業ファイルの SHA-256 が同じか確かめる（違えば作成失敗「commit されていない変更がある」）。
  3. blob から読んで計算する。
  4. 作り終えた時刻が対象日 00:00 以上なら作成失敗。
  5. 一時ファイルに書いてから、正式な名前に置き換える。
- 作成失敗の記録の保存にも失敗したとき:
  - 例外を上に返す。`run_pickup_all.py` は標準出力に印 `HORSE_STYLE_RECORD_FAILED` を出す。
  - その日の採点は、脚質を空・参照を `null` にして続ける。品質の判定で問題になり、軸の記録では「記録できない」になる。
  - `run_cron.sh` は、この印を見つけたら LINE で知らせる（`AXIS_RECORD_FAILED` と同じ仕組み）。
- 作成失敗の記録がある日に、もう一度 `run_pickup_all.py` を動かしたとき: 期限より前なら、作り直しを試す（計画 2.6）。成功したら、その成功の記録で確定する。失敗の記録は消さない。

## 4. 採点・品質・軸の記録
### 4.1 結び付け（`run_pickup_all.score_race`）
- 出馬表を確かめた後、点数を出す前に `bind_race(style_record, shutuba_data)` を呼ぶ。
  - 出馬表の取消・除外を除く全馬について、`{馬番: {"horse_id", "status", "style", "n_races", "avg_ratio"}}` を作る。
  - 状態: 「脚質あり」（`n_races` 2以上）／「1走（加点の対象外）」／「脚質なし（正常な履歴不足）」。
  - 馬IDが無い馬は「馬IDが無い」とする（出馬表の検査でもともと止まる）。
- 採点の結果のレースに `horse_style` として保存する: `{"run", "sha256", "horses": 上の結び付け}`。
- `score_horses` には、結び付けた馬だけの dict を渡す。点数の式は変えないので `SCORING_VERSION` は v5.2 のまま。脚質の版は `STYLE_BUILD_VERSION` として quality に残る。
- 作成失敗の日は、空の dict を渡す（逃げの加点は付かない）。
- `quality` に `horse_style: {"run", "sha256", "status", "version", "failure_reason"}` を入れる。
  - 作成失敗の記録もこの形で参照する。`failure_reason` は、採点のときに参照先の記録の `failure.reason` を書き写したもの（成功なら `null`）。
  - 記録が無いとき（保存にも失敗したとき）は、キーを置いて値を `null` にする。

### 4.2 部分の再実行（`rerun_failed_pickup.py`）
- 作らずに、その日の「作成成功」の記録を使う。成功が無ければ、最新の「作成失敗」の記録を使う（そのレースは品質の問題になる）。どちらも無ければ止める（計画 2.6）。
- `load_horse_style()`（`output/horse_style.json` を読む）は、採点からは呼ばなくなる。

### 4.3 品質の判定（`data_quality.race_quality_issues`）
- 品質の判定は、ファイルを読まずに `quality` の値だけで判定する（今の判定と同じ）。参照先の記録との照合は、軸の記録（4.4）と `ensure_style` が行う。
- `quality` に `horse_style` のキーがある場合:
  - 値が `null` → 「脚質の記録が無い」
  - `sha256`・`run`・`status` が無い → 「脚質の記録の形が違う」
  - `version` が無い、または知っている版の一覧（`build_horse_style.STYLE_BUILD_VERSIONS`）に無い → 「脚質の作成コードの版が無い・知らない版」
  - `status` が「作成失敗」 → 「脚質を作れない: {failure_reason}」（`failure_reason` が無ければ「脚質を作れない: 理由の記録が無い」）
  - `status` が「作成成功」「作成失敗」以外 → 「脚質の記録の状態が分からない: {status}」
- `quality` に `horse_style` のキーが無い（この変更より前の採点）→ 「脚質が旧方式（`horse_style.json`。作成の入力の記録が無い）」。脚質が誤りだと断定する書き方にはしない。保存済みの採点の結果（`quality_issues`）と軸の記録は書き換えない。

### 4.4 軸の記録（`axis_record.py`）
- `load_style_entry(date_dir, date, label, rdata, cache)` を足す。`load_prev_entry` と同じ形にする。
  - `quality.horse_style` の参照が `null` → `RecordError`（記録できない）。
  - 記録ファイルが無い・読めない・`run_id`／`target_date` が合わない・SHA-256 が参照と違う → `RecordError`。
  - 記録の `status`・`style_build_version` が `quality.horse_style` の `status`・`version` と同じか確かめる。知らない `status` は `RecordError`。
  - 「作成成功」: 採点の結果の結び付け（`rdata.horse_style.horses`）を、次のすべてで確かめる（1つでも違えば `RecordError`）。
    - 出走馬の集合: 結び付けの馬番の集合が、採点の結果の出走馬（`horse_id_map` から `scratched_nums` を除いたもの）と同じ。一部の馬が抜けている・余分な馬がいる場合は通さない。
    - 馬番と馬IDの対応: 結び付けの各馬の `horse_id` が `horse_id_map` のその馬番の馬IDと同じ。
    - 値: 各馬の `style`・`n_races`・`avg_ratio`・状態が、記録の `horses` から作り直したものと同じ（記録に無い馬は「脚質なし」）。
  - 「作成失敗」: `failure.reason`・`finished_at`・`style_build_version` がそろっていて、`failure.reason` が `quality.horse_style.failure_reason` と同じか確かめる。そろっていれば通す（品質の判定で問題になり、軸なしとして記録される）。
  - `quality` に `horse_style` のキーが無い（この変更より前の採点）: 確かめずに通す（品質の判定が 4.3 で問題にする）。
- 確かめた部分（参照と状態）を `race_key` に入れる。`files` に `horse_style: {実行ID: sha256}` を足す。
- 復元は、今の仕組み（push された commit の作業ツリーで計算する）のままで、その commit にある記録を読む。
