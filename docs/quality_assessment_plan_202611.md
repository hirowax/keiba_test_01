# 品質の判定を「方式」と「データの確認状態」に分ける案（2026-11-06・未承認。外部レビュー1回を反映）

## 1. きっかけと目的

- 目的（ユーザー、2026-11-06）: 正しいデータを取る → 正しい推奨馬を出す → 新旧を比べて、効果の高い検証の方法を確立する。
- ユーザーの指摘: 今の品質の判定（`data_quality.race_quality_issues`）の「候補の選び方が修正前」「前走データの取り方が修正前」は、この目的に照らすと要らないのではないか。
- 外部レビュー（2026-11-06）の推奨: 「方式」と「データの確認状態」を別々に記録する。旧方式に既知の不具合があることも残す。
  - 前走データの取り方が修正前であることを理由に、旧方式の再現にも使えないと一律に決めるのは強すぎる。
  - 現行方式の🔥の閾値を決める集計では、旧方式の候補を分け続ける。

### 問題
- 「データの誤り・未確認・入力不足」と「どの方式で作ったか」を、同じ「問題あり」の一覧に入れている。
- そのため、旧方式のデータは比較では使う対象なのに「問題あり」と表示される。何が分かっていて何が分かっていないのかが、理由の文字からしか読めない。

## 3. 案

### 3.1 レースごとに2つを分けて記録する

**A. 方式（どの版で作ったか）**: 版ごとに、既知の不具合と、用途ごとに使えるかを一覧（版の台帳）で持つ。

| 方式の項目 | 記録の場所 | 版ごとに持つこと |
|---|---|---|
| 馬番・馬IDの取り方 | `quality.umaban`（無ければ `collector_version`） | 既知の不具合（未記録＝枠番を馬番として読む方式） |
| 指数の読み方 | `quality.index_reader` | 未記録＝読み方が分からない |
| 候補の選び方 | `quality.candidate_rule` | 未記録＝旧方式（「*」付きを外す・同じ値は並び順） |
| 前走データの取り方 | `quality.prev_fetch` | 未記録＝旧方式（古いキャッシュの使い回し） |
| 採点の式 | `scoring_version` | 閾値の計算に混ぜてよい版の組（互換性） |
| 前走指数レース内1位の扱い | 前走データの記録の `top1_rule` | 同上 |

版の台帳の規則（2026-11-06 レビュー指摘を反映）:
- **明示して「使える」と登録した版だけを通す**。未記録の版と、台帳に無い版は「正しさ未確認」として扱う（知らない版を黙って通さない）。
- 版ごとに、判断の根拠（何を確かめたか・どの文書か・決めた日）を書く。
- 不具合の修正（例: 馬番）と定義の変更（例: 候補の選び方）を区別して書く。修正前の版は「既知の不具合がある方式」、定義の変更前の版は「別の方式」。
- **取得方式として問題ないことと、同じ閾値の集計に混ぜられることは別**。採点の式や1位の加点の条件が違えば、入力が正しくても点数の意味が変わる。閾値の計算に混ぜてよい `scoring_version`・`top1_rule` の組を台帳に書き、その組だけを同じ集計に入れる。

**B. データの確認状態（そのレースの入力について、何を確かめたか）**

| 状態 | 当てはまる場合 |
|---|---|
| 無効 | 1（`invalidated.json` に載っている） |
| 入力不足・処理の失敗 | 2、4b、7。必要な記録そのものが無い場合も含む（指数の取得経路の記録が無い、候補の前走の状態の記録が無い・候補の数と合わない） |
| 正しさ未確認 | 3、4a、6、台帳に無い版。既知なのは取得方式の不具合で、そのレースの値が誤りかどうかは確かめていない（例: 3でも枠番と馬番が一致するレースがある） |
| 誤りを確認 | 正解データと照合して、実際に不一致を見つけたレース（照合の記録を根拠として残す） |
| 必要な検査を通過 | 用途ごとに決めた検査（版の台帳・入力の記録・候補の状態）をすべて通った。何を検査したかを一緒に記録する。「問題が無いことを確認した」とは書かない |

### 3.2 用途ごとの規則を1か所にまとめる

`data_quality` に「用途を指定すると、使えるかと理由を返す」処理を1つ置き、使う側はすべてそれを呼ぶ（同じ判定を複数の場所に書かない）。

| 用途 | 使う側 | 使える条件 |
|---|---|---|
| 現行の推奨（サイト・買い目） | `run_pickup_all.py`・`rerun_failed_pickup.py`（保存）、`index.html`（保存を読む）、`paper_trade.py generate` | 方式がすべて台帳で「現行の推奨に使える」と登録した版で、確認状態が「必要な検査を通過」 |
| 現行方式の🔥の閾値の計算 | `calibrate_threshold.py` | 現行の推奨の条件に加えて、`scoring_version`・`top1_rule` が台帳で「同じ集計に混ぜてよい」組。旧方式の候補は分ける |
| 新旧の比較（タスク7） | 比較のスクリプト | この判定では決めない。比較の計画で決める。呼び方を次の2つに分ける |

新旧の比較の2つの呼び方（2026-11-06 レビュー指摘を反映）:
- **旧方式での再計算**: 同じ入力（保存した指数の表など）に、旧方式の候補の選び方を固定したコードで当てはめ直す。タスク7の比較はこれ。
- **当時の動作の再現**: 当時の入力と動作そのもの（当時の候補・点数・買い目）を再現する。当時の入力を確定できる場合だけ。不具合を含む当時の動作の記録として扱い、正しい入力での比較とは区別する。

### 3.3 保存した判定と、今の規則での判定を区別する

- サイトは採点の時に保存した理由を読み、買い目と閾値の計算は実行の時に判定する。台帳を更新すると、同じレースでも結果が食い違い得る（2026-11-06 レビュー指摘）。
- 保存する判定には、**判定規則の版・用途・判定日時**を付ける。「採点の時の判定」と「今の規則での判定」を区別して扱う。
- 過去のファイルは上書きしない。今の規則で判定し直した結果が要るときは、別ファイルに出すか、実行の時に計算して記録に残す。

### 3.4 変わること・変わらないこと

- **変わらない**: 正常な入力の、今の推奨・買い目・閾値の計算での扱い。
- **意図して変える**: 今のコードの穴。版に台帳に無い文字があっても、指数の取得経路の記録や候補の前走の状態の記録が無くても、今は理由なしで通る（レビューで再現。こちらでも 2026-11-06 に再現）。新しい判定では、これらを「正しさ未確認」「入力不足」として通さない。通常の採点ではこれらの記録が必ず入るので、本番への影響は小さいと見ている。
- **変わる**: 記録と理由の書き方。どの方式か、既知の不具合は何か、何を確かめて何が未確認か、が分かれて残る。
- **効果の大きさ**: 今日からの推奨と買い目への影響は小さい。効くのは記録の分かりやすさと、比較で旧方式のデータを選ぶときだけ。急がない。

## 4. 検証の方法（実装の前に決めておく）

過去の1,670レースは、今の判定で使えるレースが0件（2.の表）。そのため「全部を通さない」実装でも全レースで一致してしまう。一致だけでは足りないので、次を組み合わせる。

- **過去の全レース**: 新しい判定と今の判定で、使える／使えないが一致すること。方式と確認状態の内訳を2.の表と同じ区切りで数える。
- **作り物のレースでの試験**（テスト）:
  - 正常な入力（台帳に登録した現行の版・指数の記録あり・候補の状態ありで取れた）が「必要な検査を通過」で使えること。
  - 台帳に無い版、未記録の版。
  - 必要な指数の記録の欠け（取得経路の記録が無い・3つのうち欠け）。
  - 候補の前走の状態の欠け（記録が無い・候補の数と合わない）。
  - 採点の式・1位の扱いが閾値の集計で混ぜてよい組でない。
  - 境界の組み合わせ（候補の選び方だけ旧・前走だけ旧、無効・採点エラーとの重なり）。
  - 今のコードで通っていて新しい判定で通さないものは、テストの名前と文書で「意図した変更」と区別する。
- **本番のデータ**: 11/7 以降の修正後のデータで、通るべきレースが通ること（ここで初めて「使える」側の実例が入る）。
- **使う側の動作**: `paper_trade.py generate`・`calibrate_threshold.py`・`index.html` を作業用の複製で動かし、保存した判定と今の規則での判定が別々に記録されることを見る。

## 5. 決めてほしいこと

1. 「方式」と「データの確認状態」に分ける形でよいか（レビューは妥当と判断）。
2. 3.1 Bの割り当て（3・4a・6・台帳に無い版を「正しさ未確認」、照合で不一致を見つけたものだけ「誤りを確認」、条件に当てはまらないものは「必要な検査を通過」）。
3. 閾値の計算に、採点の式・1位の扱いの互換性の条件を足すこと。
4. 新旧の比較を「旧方式での再計算」と「当時の動作の再現」に分けて呼ぶこと。旧方式を使えるかどうかは比較の計画で決めること。
5. 実装の時期: 今日の本番の確認の後、タスク7（新旧の比較）の準備に合わせて、台帳と検証のケースを具体化する（レビューも同じ順序を推奨）。
