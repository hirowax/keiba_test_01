## 2. 方針
- **取得と採点を分ける。** 馬ページを取る処理は入力の記録を作るだけにする。採点は保存済みの入力だけを読む（再採点も同じ）。
- **入力の記録を唯一の正本にする。** 採点結果の前走に関する部分と `prev_data.json` は、正本から作る。
- **正常な「前走なし」と取得異常を区別する。** 取得異常を空の値や0点にしない。
- **失敗したら古い値に戻らない。**
- 加点の条件を変えるなら、採点ルールの版（`SCORING_VERSION`）を上げる。

## 3. 直し方の案

### 案A: 入力の状態と、再利用してよい条件（問題1・2・6）
各馬の入力に、次のどれか1つの状態を記録する。

| 状態 | 意味 | 採点での扱い |
|---|---|---|
| 取れた | 対象日より前の行があり、必要な列が読めた | 使う |
| 前走なし | 表を正常に読み取れ、対象日より前の行が無いと判断できた（初出走など）。条件は下の「前走なしとする条件」 | 前走の加点なし（正常） |
| 指数が「**」 | 行はあるが、指数が「**」 | 指数以外は使う。指数の加点は判定できない |
| 取得失敗 | ページが開けない、表が無い、見出しが見つからない、日付を読めない行がある、値が範囲外、前走なしと判断できないなど | 使わない。取得異常として記録する |

- 「指数が「**」」は、画面で「**」と表示されていたという観測の記録。原因（非公開など）は確かめるまで書かない。
- 前走なしとする条件（すべてを満たすときだけ。1つでも満たさなければ取得失敗）:
  - 表 `table.db_h_race_results` があり、見出しから必要な列を特定できた
  - 表の全部の行で、日付を `YYYY/MM/DD` として読めた（読めない行が1つでもあれば取得失敗）
  - 対象日より前の日付の行が1つも無い（行が0件の表を含む）
  - 表が途中で切れていない（ページの読み込みが終わってから読む。全成績が別ページに分かれる形のページなら、その扱いを実ページで確かめてから書く）
  - 「前走なし」の馬も、版・期限の条件を満たさなければ再利用しない
- 再利用してよい入力（すべてを満たすもの）:
  - 状態が「取れた」「前走なし」「指数が「**」」
  - 同じ対象日のために取った値（`target_date` が一致）
  - 取得の処理の版（`PREV_FETCH_VERSION`）が今と同じ
  - 取得の期限より前に取った値。期限は「対象日の前日の24時まで」とする案（前日17時の実行と、その日の再実行が入る。当日朝の再実行を許すかは「決めてほしいこと」5）
    - 判定は日本時間で、その馬のページの取得が終わった時刻（取得完了時刻）で行う。境界は「対象日の 00:00:00 より前」なら期限内、00:00:00 ちょうど以降は期限後（例: 対象日 11/7 なら、11/6 23:59:59 は期限内、11/7 00:00:00 は期限後）
- 「取得失敗」は再利用せず、次の実行で取り直す。取り直しも失敗したら「取得失敗」のまま記録する。前の値には戻らない。
- 期限の後に取った値は「期限後の取得」として別に記録する。当時の採点入力とは呼ばず、採点にも使わない。
- 28日・7日の有効期限と、絶対値の条件はやめる。今の `horse_db.json` の値（`target_date` も版も無い）は使わない。
- 馬ページで選ぶ行は今と同じ（対象日より前の、いちばん新しい行）。自前の結果で出走が見つからないことは、出走していない証拠にしない（計画6章）。

### 案B: 比較相手も、その対象日に馬ページを取る（問題3）
- 採点するレース（3指数すべてでトップ3の馬がいるレース）の、取消・除外を除いた全馬を取る。
- 取得する量（参考の値）: 採点したレースは 11/1 が8レース106頭、10/31 が4レース46頭。2日分だけなので、上限やアクセス制限が起きないことの保証には使わない。
  - 所要時間は見積もらない。取得の関数には待機のほか、スクロールや途中のページへの移動もあるため。作業用の複製で試すときに測る。
- 一部の馬の値が分からないときの前走指数レース内1位は、「決めてほしいこと」1 で決める。推奨は保留（加点しない・保留と記録する）。

### 案C: 列を見出しで特定する（問題5・6）
- 馬ページの表 `table.db_h_race_results` の見出し行から、「日付」「人気」「着順」「距離」「指数」などの列を名前で探す。見つからなければ「取得失敗」にする。
- 前走のレースID は、行の中のレースへのリンク（`/race/XXXXXXXXXXXX/`）から取る。
- 範囲の検査: 指数は、指数の表と同じく200以上を異常（取得失敗）にする。0とマイナスは正当な値。
- 見出しの実際の文字と、添字21（`prev_idx_m`）が何の値かは、**実ページで確かめてから**コードに書く。結果の取り直しが終わってから、馬ページを数頭分だけ開き、保存して `tests/fixtures/` に入れる。
- 「**」が出る馬について、同じ馬ページをログインした状態で開いて確かめる（「**」とログインの関係は、確かめるまでは仮説）。

### 案D: 入力の記録（正本）の形（問題7）
- 置き場所: `output/{日}/prev_inputs/{実行ID}.json`。1回の実行で1ファイル。
  - 一時ファイルに書いてから名前を変える。途中で止まっても、既存の記録は壊れない。
  - 同じ日の二重起動は、ロックファイルで止める。
- 中身: 実行ID → レースID → 馬ID。
  - 実行: 実行ID、開始・終了の日時、コミット、`PREV_FETCH_VERSION`、`SCORING_VERSION`、再利用した入力の元の実行ID
  - 馬ごと: 状態（案A）、対象日、取得日時（秒まで）、取り方（その場で取得／再利用）、選んだ行の日付・レース名・レースID、見出しの文字、各列の元の文字、変換後の値（指数・人気・着順・距離）
  - レースごと: 比較対象にした馬と外した馬・外した理由（取消・除外・前走なし・指数が「**」・取得失敗）、使った最大指数、前走指数レース内1位の判定（1位／1位でない／保留）と方針の版
- `pickup_scores.json` の各レースに、採点に使った実行IDを書く。
- `prev_data.json` は、採点結果が参照する実行の記録からだけ作る派生ファイルにする（今の形を保ち、`rescore.py` などとの互換のため）。
- 通常の再実行（`rerun_failed_pickup.py` など）: 再利用してよい入力はそのまま使い、取得失敗の分だけ取り直す。新しい実行IDの記録に、再利用した元の実行IDを書く。
- 成功した入力を取り直すのは、明示の操作（例: `--refetch`）だけにする。新しい記録として残し、古い記録は消さない。
- 再実行の対象の判定（`rerun_failed_pickup.py` 42〜50行。今はレースの `error`、または「候補全員0点かつ人気が空」だけ）に、次を足す:
  - 候補または比較相手に「取得失敗」の馬がいるレース → 自動で再実行の対象にする（他の加点があっても対象）
  - 「指数が「**」」の馬がいるだけのレース（前走指数レース内1位の保留を含む） → 自動の再実行の対象にしない。件数を報告する
  - 判定は記録（案D）の状態から行い、`pickup_scores.json` の点数からは推測しない

### 案E: 版・取得結果・品質の判定（問題4・8）
- 版と取得結果を別々に記録する。各レースの `quality` に足す:
  - `prev_fetch`: `PREV_FETCH_VERSION`
  - `prev_inputs_run`: 採点に使った実行ID
  - `prev_status`: 候補ごとの状態、比較相手の状態ごとの頭数、前走指数レース内1位の判定
- `data_quality.race_quality_issues()` に足す判定（案）:
  - `prev_fetch` が無い → 「前走データの取り方が修正前」（今までの全データが当たる）
  - 候補に「取得失敗」がある → 「候補の前走データが取れていない」
  - 前走指数レース内1位が保留 → 品質の問題とはせず、件数を報告する（保留は決めたルールどおりの結果なので）。扱いは「決めてほしいこと」1 とあわせて決める
- 呼び出し元への反映（今は `calibrate_threshold.py` だけ）:
  - `paper_trade.py`: 買い目の生成と精算で、品質に問題があるレースをどう扱うか（買い目を作らない／作って印を付ける）。「決めてほしいこと」6
  - `index.html`: 品質に問題があるレースに印を出すか
  - 実装の前に、`pickup_scores.json` を読む処理をすべて洗い出す
- `rescore.py`:
  - `horse_db.json` からの補完をやめる。
  - 新方式に対応するまでは、`prev_inputs/` がある日は止める（エラーで終わる）。
  - 対応した後は保存済みの入力だけで採点し、`quality` を作り直す（元の `quality` を残さない）。
  - 過去日付に実行しない決まりは変えない。

### 案F: 処理を1つにまとめる（問題9）
- 取得は1つの関数にする（例: `fetch_prev_inputs(page, date, race_id, horse_ids, reusable)`）。`run_pickup_all.py` と `rerun_failed_pickup.py` の両方から呼ぶ。
- 採点に渡す前走の値を、記録から作る関数も1つにする（例: `prev_db_from_inputs(record)`）。`run_pickup_all.py`・`rerun_failed_pickup.py`・`rescore.py` から呼ぶ。
- `scrape_prev_data.py`（cron・`run.sh` からは呼ばれていない）は、同じ関数を呼ぶか、使わないものとして止めるかを決める（「決めてほしいこと」4）。
- 研究用のスクリプト（`analyze_anaba*.py` など。2026-05 から保留）は変えない。`horse_db.json` を読んでいることを、冒頭の注意書きに足す。

### 案G: テスト
`python3 -m unittest discover -s tests` に足す。馬ページは実ページの保存（案C）を使う。
- 見出しから列を探す。見出しが無い・形が違うときは取得失敗になる。
- 行の選び方: 対象日と同じ日の行（当日のレース）を選ばない。対象日より前の最新の行を選ぶ。
- 4つの状態の区別。「**」・空・0・マイナス・200以上の指数。
- 再利用: 同じ対象日・同じ版・期限内の成功した入力だけを使う。取得失敗・別の対象日・別の版・期限後・`target_date` が無い値は使わない。
- 取り直しが失敗したとき、前の値に戻らない。
- 前走なし: 正常な初出走（表はあり行が0件・全行の日付が対象日以降）は「前走なし」。日付を読めない行がある、表が無い、見出しが無い、表が途中で切れている場合は「取得失敗」。
- 期限: 取得完了時刻が対象日の前日 23:59:59 は期限内、対象日 00:00:00 は期限後（日本時間）。
- 再実行の対象: 候補だけ・比較相手だけに「取得失敗」があるレースは、他の加点があっても対象になる。「指数が「**」」だけのレースは対象にならない。
- 比較相手の一部が分からないときの前走指数レース内1位（決めた扱いのとおりになるか）。
- 記録: 途中で止めても既存の記録が壊れない。二重起動を止める。再実行で記録が上書きされない。`prev_data.json` が、参照する実行の記録だけから作られる。
- `rescore.py` が `horse_db.json` から補わない。新方式の日は止まる。
- 品質の判定: 版が無い・候補が取得失敗のレースを外す。

### 案H: 実装後の確認
- テストに加えて、作業用の複製で1日分を試す（取得するページ数と所要時間を測る）。
- 次の開催日の実行で、記録の選んだ行の日付と指数を、指数の表の「前走」の列と全頭で照合する（一致率は列の意味の証明にしない）。
- 結果が取れた後に、選んだ前走より後に自前の結果で出走が無いかを確かめる。`verify_results.py` に足すかは別に相談する。

## 5. 日程と、間に合わない場合
- 次の自動取得は 2026-11-06（金）17:00（11/7 の分）。
- 結果の取り直しは 11/5 の10〜11時ごろに終わる見込み。その後なら馬ページを開いて確かめられる（案C）。
- 案C の実ページの確認が済むまでは、列を見出しで特定する部分を書けない。全部を 11/6 17:00 に間に合わせるのは難しい見込み。
- 間に合わない場合の扱い（「決めてほしいこと」3）。今のコードのまま動かすと、品質の判定では除外されない（案E がまだ無いため）。表示・買い目も別の経路なので、そのまま出る。
  - (a) 先に、品質の判定に「前走データの取り方の版が無い」を足す変更だけを入れる（小さい変更とテスト）。11/7 の分は研究・閾値調整から外れる。表示と買い目はそのまま出る。
  - (b) (a) に加えて、11/7 の分を旧方式の参考の出力として扱う。サイトに印を出し、ペーパートレードの買い目に旧方式と記録する。
  - (c) 11/7 の採点（`run_pickup_all.py`）と買い目の生成を止め、指数の表だけを公開する。
- 進め方の案: (1) 間に合わない場合の扱いを決め、必要ならそれだけ先に入れる → (2) 実ページの確認と保存 → (3) 案A〜F をまとめて実装し、テストを足す → (4) 作業用の複製で1日分を試す → (5) 承認を得て main に入れる。

## 6. 決めたこと（2026-11-05 ユーザー決定）
外部レビュー（2回目）の推奨どおりに決めた。

1. 比較に必要な値が分からない馬（取得失敗・指数が「**」）がいるときは、前走指数レース内1位の加点を保留する（加点しない・保留と記録する）。正常と確かめた前走なし（案A の条件）の馬は比較の対象外。
2. 1 の条件の変更と同時に `SCORING_VERSION` を上げる。
3. 11/6 17:00 に間に合わない場合は (c): 11/7 の採点（`run_pickup_all.py`）と買い目の生成を止め、指数の表だけを公開する。期限のためだけの暫定の処理は増やさない。
4. `scrape_prev_data.py` は、実行したら理由を表示して止まるようにする。削除はしない。
5. 取得の期限は対象日の前日24時で固定する（判定は案A のとおり）。当日朝の再実行は許さない。
6. 品質に問題があるレースは、ペーパートレードの買い目を作らない。サイトには理由を表示し、通常のおすすめの順位・🔥の表示から外す。
